# C2.2 第一关完整性修复报告

## 结论

第一关确实还有程序缺陷，不能直接归因为“门槛太高”。本轮已把已确认缺陷修到正式数据，现在的程序事实是：

- 15,794 条市场已确认对象已显式进入第一关队列；
- 15,693 条已完成，101 条只在等待原子资格批次，无理由卡住为 0；
- 12 条通过当前宽硬门槛；C2.1 前台、C2.2 前台和凸性跟踪输入都是 12；
- 凸性跟踪已经有工作对象，不再是第一关结果未交接的状态。

但 15,561 条 90 天内完成对象最终只有 15 条形成 A/B/C 项目关系与合格产品证据交集。这是当前最大收缩点，不是 P60、成交额、流动性或其他市场数值门槛。

## 修复了什么

1. **第一关队列状态可对账恢复**
   - 中断的修复进程一度把大量已有有效评估的队列留在 `pending`。
   - 现在按资格批次、规则哈希和输入时间恢复可复用结果；只有真正过期的才重算。

2. **公开市场确认后正式进入候选资产核验**
   - 修复前，11,999 条已通过本地检查且市场已确认的对象仍停在内部 `unknown`，因而网站和 GitHub 核验会跳过它们。
   - 现在它们会进入 `candidate_asset`，但不会直接升为 C，仍必须通过身份和产品证据。

3. **新形成的合格产品证据可以把 D 正确升为 C**
   - 修复前只会降级不合格 C，不会在新证据形成后升级 D。
   - 现在只有“候选资产＋身份闭环＋任一合格产品证据”同时成立才升为 C。

4. **GitHub 产品证据与资产身份分开判断**
   - 仓库真实不等于该仓库属于该代币。
   - 身份未闭环时，GitHub 只能保留为待确认证据，不能绕过 D 类边界。

5. **评估恢复性能修复**
   - 新增候选 ID＋当前评估索引，避免每个候选重复扫描评估集合。
   - 15,693 条本地重算用时 17.8 秒，不需要任何外部接口或历史重扫。

## 真实漏斗

| 阶段 | 剩余 | 相比上一阶段减少 |
|---|---:|---:|
| 第一关已完成 | 15,693 | - |
| 仍在 90 天内 | 15,561 | 132 |
| A/B/C 项目关系 | 15 | 15,546 |
| 身份一致且有合格产品证据 | 15 | 0 |
| 当前硬门槛通过 | 12 | 3 |
| 前台与凸性跟踪输入 | 12 | 0 |

身份一致对象共 253 条，合格产品证据对象共 44 条，两者交集只有 15 条。这证明当前要优先讨论的是“第一关要求多强的项目身份和产品证据”，而不是继续降低成交额或 P60 数值。

未进入前台的 3 条 A/B/C 对象中，2 条因最新真实窗口没有可用买入事实而失败，1 条因风险来源未完成而保持 `pending`。

## 程序上限与未解决边界

- 程序可以核验链、合约、交易池方向、官方网站链接、官方仓库和结构化协议数据；不能从名称相似或项目宣传自动猜测代币与项目关系。
- `deployed_product` 和 `token_utility` 首版仍是 `unsupported`，因为还没有跨项目通用且可确定归属的解码来源。产品正确选择明示不支持，没有伪造结论。
- 本轮网站核验有 151 个连接失败，全部记为 `source_failure`，不是 `no_data`；这些对象后续可按来源游标重试。
- 12 条是自动研究线索，不等于项目靠谱、低估或未来会涨，也不代表程序可以代替投资决策。

## 下一优先级

不再继续盲目降低市场数值门槛。下一步应该基于这份真实漏斗，单独讨论第一关的“项目身份与产品证据”政策是否过严，以及哪些程序可采集证据可以作为更宽的候选资格。这属于规则变更，本轮没有擅自修改。
