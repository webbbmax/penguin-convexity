# 企鹅投研-凸性｜C2.1 正式产品需求

状态：正式冻结；等待实现；产品代码未开始  
版本名称：C2.1「90 天新发项目自动筛选与可解释前台」  
冻结日期：2026-08-10（Asia/Shanghai）

正式规则配置：`docs/C2.1_RULE_CONFIG.json`  
正式回归清单：`docs/C2.1_RULE_REGRESSION_MANIFEST.json`

## 1. 一句话结论

C2.1 不把 Gate 0 的 4,585,955 个候选代币直接当成新项目，也不承诺“自动找到靠谱币”。它把已验收的 90 天 DEX 创建证据生产化，经过身份归并、T0、A/B/C/D、买卖事实、显性硬风险和产品证据筛选后，把全部通过宽硬门槛的项目放进前台，再用可复算证据区分“凸性线索、活跃项目、观察中和数据受限”。

本稿给出可直接冻结的完整候选范围。用户明确回复冻结前，不生成正式需求锁，不修改 C2.0 产品、主数据库、现有调度或前台页面。

## 2. Gate 0 已经证明和没有证明的能力

### 已经证明

- 固定 90 天窗口、六条链、冻结登记协议范围可以分片、断点续跑、恢复和独立复算。
- 正式结果为 262/262 分片、5,922,807 条创建事件、4,585,955 个唯一候选代币。
- 结果可重复计算；完成后再次触发不会增加网络请求或改写结果。
- 来源请求可以区分成功、无数据、额度受限、来源失败、不支持、配置缺失和程序失败。

### 没有证明

- 4,585,955 个候选不是 4,585,955 个项目，其中包含交易对两侧资产、旧币新池、包装资产、重复关系和只有代币的对象。
- 池创建时间只是已覆盖 DEX 中的公开池证据，不自动等于全市场首次公开流通时间。
- Gate 0 没有完成项目身份、GitHub 映射、买卖交易、合约安全、流动性历史、钱包、持仓和五因子全量闭环。
- Gate 0 不证明全市场覆盖，不证明项目靠谱，不证明市场低估，也不证明未来上涨。

因此 C2.1 的第一项开发工作必须是“候选母池生产化”，不是直接写前台或直接计算综合分。

## 3. C2.1 的正式产品目标

C2.1 只交付以下六项能力：

1. 复用 Gate 0 已验收结果，并从最后游标开始做日常增量发现，不重跑已完成的 90 天全量扫描。
2. 对接入范围内的全部候选执行确定性本地归并和基础扫描，不随机抽样、不设置热门项目上限。
3. 对确定性通过前置条件的对象采集 T0、身份、买卖、产品证据、行情和显性风险。
4. 全部通过宽硬门槛的 A/B/C 对象进入前台，D 类留在后台；综合分不控制前台资格。
5. 用强证据路径定义“凸性线索”，用弱证据路径定义“活跃项目”，其余项目继续可见并说明原因。
6. 手动更新和可选自动更新使用同一条流水线；来源失败时保留上次完整快照并明确显示数据时间。

## 4. 首版支持范围

### 4.1 发现范围

首版只承诺 Gate 0 已验收的六链登记范围：

| 网络 | 已验收的 EVM 标签或 Solana 创建指令范围 |
|---|---|
| Ethereum | Uniswap V2、Uniswap V4 |
| Base | Uniswap V2、Uniswap V4 |
| Arbitrum | PancakeSwap V2、SushiSwap |
| BNB Chain | Four.meme、PancakeSwap V2/V3/Infinity CLMM、Uniswap V4 |
| Robinhood Chain | Bankr、pons.family、SushiSwap V3、Uniswap V2/V3/V4、Virtuals |
| Solana | 已验收登记表中的 13 种创建指令，覆盖 Pump.fun、PumpSwap、Meteora、Orca、Fluxbeam 等已确认标签 |

Ethereum 4、Base 8、Arbitrum 6 个未确认标签继续记为 `unsupported`，不得猜测解码，也不得在前台写成已覆盖。

### 4.2 补充数据来源

- DEX 与行情：GeckoTerminal、DexScreener，以及已接入的链上池和交易数据。
- 链上数据：Alchemy、Helius、NodeReal、Blockscout、SQD；按已验证网络和字段使用，不假定每个来源覆盖六链全部字段。
- 安全：GoPlus 作为显性风险证据之一，不作为唯一安全门槛；无返回不能写成安全，也不能自动写成项目失败。
- 项目与市场映射：官方入口、GitHub、CoinMarketCap 和现有项目库；聚合平台只能提供候选映射，官方关系仍需可复现证据链。

前台固定显示“接入范围”，不得简称“全市场”。

## 5. 候选处理漏斗

每个发现对象依次经过：

1. **事件归并**：按链、合约、池、连续资产关系去重，识别交易对两侧资产、稳定币、包装币和已知旧资产。
2. **疑似新发资产**：检查已覆盖来源中是否存在更早公开流通证据；发现早于 90 天的证据即退出新发池。
3. **T0 证据**：保存目前查到的最早公开流通事件、来源、覆盖范围和冲突状态。
4. **A/B/C/D 分类**：能确定新项目为 A，能确定老项目新币为 B，关系无法确定但已有项目证据为 C，只有代币为 D。
5. **宽硬门槛**：判断是否进入前台。
6. **深度采集**：对所有硬门槛通过对象采集五因子输入和证据路径，不设固定项目数上限。
7. **状态与快照**：计算项目状态、排序理由和重要变化，原子发布前后台快照。

所有候选都进入确定性本地基础扫描；只有通过明确前置条件的对象才消耗高成本接口。这里的分层是成本控制，不是随机抽样。

## 6. T0 与 A/B/C/D 的可实现口径

### 6.1 T0 前台名称

前台统一显示：

> T0（目前查到的最早公开流通证据）

程序保存 `t0Scope`，说明它来自哪些链、DEX、交易场所或官方领取证据。不得写成“已证明的全球首次流通”。以后发现更早证据时，T0 可以向前修正，并形成一条重要变化记录。

### 6.2 T0 状态

- `verified_in_supported_scope`：事件真实、时间可复现、资产身份一致，可参加 90 天筛选。
- `conflict`：可靠来源之间的时间或资产关系冲突，只留后台。
- `not_verified`：只有宣布、程序首次发现或数据库时间，只留后台。

程序首次收录时间只计算发现延迟，不参与项目年龄。

### 6.3 分类边界

- A 只有在项目身份和官方资产关系明确，且没有已识别的旧项目连续关系时成立。
- B 只有在旧项目身份和新资产关系都有确定性证据时成立。
- 无法可靠区分 A/B，但存在合格产品证据时进入 C，并固定显示“项目关系未确认”。
- 无官网、产品、代码、部署、业务或已执行代币功能证据时进入 D，不进前台。

程序不会为了提高 A 类数量猜测项目年龄或主体关系。

## 7. 宽硬门槛

对象同时满足以下六项才进入前台：

1. T0 状态为 `verified_in_supported_scope`，当前为第 0—90 天。
2. 分类为 A、B 或 C。
3. 代币合约、网络、交易池和资产方向一致。
4. 已观察到真实公众买入与真实公众卖出；历史卖出只证明当时可卖，不保证未来可卖。
5. 当前没有已确认的卖出失败、冻结转账、黑名单生效、流动性归零/撤出、资产身份冲突等硬阻断。
6. 至少有一类合格产品证据：官方非空代码仓库、已部署产品合约、结构化业务数据、已执行代币功能或可复现链上产品使用。

首版不把固定成交额、固定市值、固定 TVL、综合分、满 14 天或五因子齐全设为前台硬门槛，避免再次出现“程序有数据但前台一条也没有”。极低流动性和资料缺口必须醒目标记，但不在没有用户确认时临场加严。

GitHub 单独满足产品证据时，前台固定写“仅代码证据；不证明产品部署、用户采用或投资价值”。官网、文档、社交热度、涨幅和普通转账不能单独满足产品证据。

## 8. 前台五种互斥状态

每个硬门槛通过项目只能处于一种状态，优先级固定为：

1. `data_limited` 数据受限：关键字段因额度、来源、回溯或时效问题无法作当前判断。
2. `convexity_clue` 凸性线索：符合第 9 节强线索算法。
3. `active_project` 活跃项目：不满足强线索，但符合第 10 节弱线索算法。
4. `early_observation` 新发观察：真实历史不足 14 天，尚未形成强/弱线索。
5. `continuous_observation` 持续观察：真实历史已满 14 天，尚未形成强/弱线索。

14 天只改变观察标签和可用比较窗口，不是项目等待期，不影响前台资格。所有项目只使用来源返回的真实历史，未来日期不计零。

## 9. 强线索算法：何时可以叫“凸性线索”

### 9.1 五因子

| 因子 | 固定权重 | 可程序采集的主要输入 |
|---|---:|---|
| D 交易需求 | 25% | 买卖次数、成交额/流动性、活动日、独立与重复交易地址（来源支持时） |
| L 流动性与退出 | 25% | 流动性/FDV、标准金额退出滑点、流动性保留和最大回撤 |
| S 持币与供应 | 20% | 非尘埃地址、头部集中度、HHI、Mint/Burn 和净供应（来源支持时） |
| G 活动与估值关系 | 15% | 成交额/FDV、活动增长相对估值变化、可核验产品使用变化 |
| Q 稳定性与异常 | 15% | 单日成交集中、地址集中、价格/流动性异常和跨来源偏差 |

钱包数只能写成“链上地址数”，不能写成真实用户数。刷量、女巫和关联钱包只能按可检测规则降权，不能声称完全识别。

### 9.2 四条强证据路径

#### 路径一：交易与流动性形成（必选）

项目必须同时满足：

1. 最新流动性不低于“同链同日龄 P60”和年龄美元护栏两者中的较高值。
2. 当前真实窗口内买入不少于 1 笔、卖出不少于 1 笔。
3. 成交额、交易笔数、成交额/流动性三项中至少两项达到同链同日龄 P60。
4. 100 美元标准卖出报价成功，估算损失不高于 10%。报价缺失或该网络不支持时，本路径为 `unavailable`，不能补零或冒充通过。
5. 没有第 9.4 节严重异常。

年龄美元护栏固定为：

| 真实日龄 | 最低流动性 |
|---|---:|
| 0—2 天 | 2,000 美元 |
| 3—6 天 | 2,000 美元 |
| 7—13 天 | 3,000 美元 |
| 14—30 天 | 3,000 美元 |
| 31—90 天 | 5,000 美元 |

P60 比较组优先使用最近 30 天同链同日龄至少 20 个有效对象；不足时使用同日龄六链至少 50 个有效对象；仍不足时使用冻结规则配置中的年龄后备基线。缺失值只退出该指标分母，不写成 0。

#### 路径二：真实产品使用扩张（有数据才启用）

项目合约、产品合约或结构化业务指标必须有确定性身份映射，并在两个等长、已完成窗口中使用完全相同的指标定义。当前值必须同时满足：不少于 5、比前一窗口至少增加 3、增幅不少于 20%。价格、社交人数、Star 或项目方宣布不能构成本路径。没有真实时间序列时固定为 `unavailable`，不影响前台资格。

#### 路径三：供应与需求结构改善（有历史才启用）

历史单位必须稳定，且以下任一项成立，同时交易活动不低于同组 P50：

- 前十地址占比较前一等长窗口下降至少 5 个百分点；
- 持仓 HHI 较前一等长窗口下降至少 10%；
- 总供应较前一等长窗口减少至少 0.5%。

只有当前快照、供应完全不变或持仓接口无历史时，本路径为 `unavailable`。供应稳定只作为异常与可信度证据，不能单独形成强路径。

#### 路径四：已索引池活动超过供应修正估值变化

本路径只汇总数据来源已经索引并能返回 OHLCV 的池，不得简称“全球全池”。必须同时满足：

1. 来源已索引池的所需 OHLCV 全部完整；本地发现但未索引的池单独显示数量、降低可信度，不补零，也不自动淘汰项目。
2. 历史总供应读取成功，前后计量单位一致。
3. `成交活跃变化 = ln((当前窗口日均成交额+1)/(前一窗口日均成交额+1))`。
4. `供应修正估值变化 = ln((当前价格×当前供应)/(前一价格×前一供应))`。
5. `相对扩张 = 成交活跃变化 - 供应修正估值变化` 达到同日龄 P60。
6. `风险修正剩余 = 成交活跃变化 - abs(供应修正估值变化)` 大于 0。
7. 没有第 9.4 节严重异常。

0—6 天使用两个等长完整小时窗口，单边最少 6 小时、最多 24 小时；7—30 天使用前 3 个完整自然日与后 3 个完整自然日；31—90 天使用前 7 日与后 7 日。未形成所需真实窗口时路径为 `forming`，不是缺失或失败。

### 9.3 凸性线索成立条件

项目必须同时满足：

1. 宽硬门槛通过，数据状态不是中断。
2. 至少三项五因子具有真实观测，不以缺失或先验冒充实测。
3. 至少形成两条强证据路径，其中必须包含“交易与流动性形成”，第二条来自产品使用、供应需求或活动估值关系。
4. 证据至少来自两种独立来源类型，不能只由同一聚合接口的多个字段重复计数。
5. Q 因子没有触发冻结的严重异常护栏。

综合分无论多高，都不能单独把项目变成凸性线索。首版现实可用的主要组合是“交易与流动性形成＋已索引池活动超过供应修正估值变化”；产品使用和供应需求路径保留，但只有真实历史存在时才参与。路径一和路径四组合时，必须同时具有市场池数据与链上历史供应两种来源类型，不能只重复使用同一聚合接口字段。

### 9.4 异常与进入/退出防抖

- 跨来源价格偏差达到 25% 时视为数据冲突，相关路径转为 `unavailable`，不把冲突写成项目风险或 0。
- 相邻可比窗口流动性下降达到 80%、100 美元卖出估算损失达到 20%、供应计量单位改变，均立即撤下“凸性线索”标签并重新计算资格。
- 已确认卖出失败、冻结、黑名单或第 91 天到达，立即执行硬门槛退出，不等待防抖。
- 正常进入只需一次完整评估，但所需的前后真实比较窗口必须已经形成，不要求项目再等待固定天数。
- 正常退出需要两个新的、连续完成的评估窗口均低于退出规则；退出比较使用同组 P50。相同窗口的重复调度不累计次数。
- 来源失败、额度受限和配置缺失不算一次“未通过”；项目保留上次完整结果并进入“数据受限”。
- 最大池成交占比和池 HHI 只作为集中度提示，不能单独判定刷量或直接淘汰项目。

## 10. 弱线索算法：何时显示“活跃项目”

活跃项目必须已经通过宽硬门槛、不是数据中断、尚未形成凸性线索，并至少满足一条可复算活动证据：

- 交易次数、成交额或成交额/流动性至少一项达到同链同日龄 P70，且观察到真实买入和卖出；
- 官方非空代码仓库在最近 30 天有非文档类自有提交；
- 已验证产品合约或业务指标出现真实新增使用；
- 流动性连续两个完整窗口高于年龄美元护栏，期间回撤小于 50%，且没有同步出现严重退出异常。

“活跃项目”只表示近期有真实活动，不表示靠谱、低估、安全或值得买入。单纯价格上涨、Star、粉丝数和项目方宣传不构成活跃证据。

## 11. 动态经验贝叶斯评分与独立可信度

### 11.1 分数用途

五因子综合结果只用于后台排序、变化检测和以后校准。前台可以显示“改善/稳定/减弱/不可用”及排序理由，不显示“多少分等于凸性线索”。

### 11.2 计算原则

- 比较组按同链和同真实日龄阶段划分：0—2、3—6、7—13、14—30、31—90 天。
- 连续指标先做对数和稳健异常值处理，再转成同组百分位，避免极端刷量直接支配结果。
- 每项观测用同组先验做经验贝叶斯收缩；样本少时更接近中性先验，样本增加后更多由项目自身数据决定。
- 缺失字段不写 0、不跨因子重新分配权重；使用先验时必须同时扩大不确定区间，并标记“无实测”。
- 短历史项目用 `effectiveWindowDays=min(ageDays+1,14)` 计算真实覆盖率，与同日龄对象比较；不存在年龄加分或年龄扣分。
- 同一输入、同一规则版本必须得到相同结果，模型不得自由生成分数。

### 11.3 独立可信度

可信度与证据分分开计算，建议固定为：字段覆盖 35%、数据时效 25%、真实历史覆盖 20%、跨来源一致性 20%。历史覆盖的分母是项目真实可观察窗口，不是强行要求 14 天。

### 11.4 “越来越准”的真实边界

C2.1 可以随着新增真实数据持续更新项目分数，但不能宣称已经“越用越准”。C2.1 只负责保存 7/14/30 天的硬门槛保留、流动性保留、线索持续、产品证据升级和后来发现的硬风险等结果标签。C2.2 才能使用未参与参数设定的后续时间段做时间外校准；校准对象是证据持续性和风险识别，不是收益率保证。

## 12. 日常增量采集与更新控制

### 12.1 用户控制

后台更新中心提供：

- `立即更新`：执行一次完整增量流水线。
- `仅手动`：不创建周期运行。
- 可选自动频率：每小时、每 3 小时、每 6 小时、每 12 小时、每天。
- `暂停`：停止后续自动触发，不中断已经原子提交到安全点的状态。

发布迁移时原样继承当时的用户启停与频率设置，不擅自从暂停改为开启，也不擅自从开启改为暂停。以后由用户自己选择是否自动运行；这与“零人工项目复核”不冲突，因为用户只决定何时采集，不逐项目审批内容。

首版不再创建第二个长期 Windows 调度器，也不复用已经禁用的一次性 Gate 0 回扫任务。开发期间保持现有 `PenguinConvexity-C1.8-Scheduler` 不变；C2.1 发布时只把同一产品更新入口迁移到统一增量运行器，并保留原暂停值、单实例和回滚能力，避免两个任务重复采集。

### 12.2 同一条流水线

手动和自动更新都执行：发现增量 → 归并 → T0/身份 → 宽硬门槛 → 深采 → 五因子/状态 → 重要变化 → 原子快照。手动更新不绕过额度、限速、单实例锁或数据质量规则。

### 12.3 更新频率与字段频率分离

- 新池、资格和重要变化：每次运行。
- 行情与流动性：每次运行，但遵守来源限速和缓存。
- 安全、持仓与供应：新项目优先；无变化时可按日复查。
- GitHub 与产品证据：默认每日复查；发生身份变化时立即重查。

用户选择“每小时更新”不等于每个高成本接口每小时全量重扫。

### 12.4 首次生产化

C2.1 首次构建读取已验收 Gate 0 结果，并从其最后时间游标补齐增量；不得重新请求已完成的固定 90 天区间。首次转换和高成本深采必须分片、可恢复、单实例并有可读进度；完成后才原子替换前台快照。

### 12.5 手动与自动如何更新数据库

- 手动点击“立即更新”和自动到点运行都只写 `data/c2.1-pipeline.db`，调用同一增量运行器、同一规则和同一原子快照发布流程。
- 数据库使用单写入者锁和事务。每个分片先写数据并提交，再推进来源游标；事务失败时游标不前进，因此不会把未完成数据当作完成。
- 读取使用 SQLite WAL 或等价的并发只读模式；页面不直接读取正在写入的中间表，而是读取上一次完整快照。
- 手动启动后，用户离开更新中心或关闭产品窗口，已经授权的任务仍继续。手动/自动只决定“谁发起任务”，不改变恢复能力。

### 12.6 黑框与后台隐藏

- 正式桌面版统一通过 Windows 隐藏任务和 `wscript.exe` 零窗口启动独立 Python 运行器，不直接弹出 `python.exe` 或 PowerShell 控制台。
- 自动到点、手动立即更新、断点恢复和失败重试都使用同一隐藏入口，正常情况下桌面黑框出现次数必须为 0。
- 只有开发者主动从终端运行诊断脚本时才可能看到控制台；这不属于普通产品路径。
- Windows 任务保持单实例；上一个任务未结束时，新触发只记录“已有任务运行中”，不得启动第二份数据库写入。

### 12.7 断点、重试和断网恢复

- 每个来源和分片独立保存区块/Slot、分页、项目批次、最近成功时间和下一游标；关闭程序、进程异常或关机后都从最后一次已提交游标继续，不从 90 天起点重跑。
- 单次请求遇到超时、断线、TLS、429 或上游 5xx 时，先按 5 秒、15 秒、60 秒做最多 3 次后台重试；成功后清零该来源连续失败次数。
- 3 次仍失败时不做无限快速连接：保存断点，进入 `source_failure` 或 `quota_wait`。普通来源失败按 15 分钟、30 分钟、60 分钟、最长 6 小时逐级冷却；额度问题优先使用接口返回的重置时间。
- 同一个隐藏 Windows 任务可以每 15 分钟快速唤醒检查“是否有到期的新采集或应恢复的旧任务”。用户选择的每小时/每日频率只控制新一轮采集，不阻止已经授权但未完成任务的断点恢复。
- 连续失败超过 24 小时后，来源进入“长期中断”，改为每 6 小时探测；恢复后自动续采和复算，不要求逐项目确认，也不会丢弃已成功来源的数据。
- `authentication_failed`、`configuration_missing` 和 `program_failure` 不无限重连；它们在后台显示需要修复的具体原因，并保持旧快照。修复后从原断点恢复。
- 用户明确点击“暂停当前任务”才停止恢复；“仅手动”只是不自动发起新一轮，不会撤销已经点击开始的任务。

### 12.8 关闭窗口、关机和重新开机

- 关闭产品窗口或关闭 Codex：独立隐藏任务继续运行。
- 电脑关机或休眠：采集停止，已提交断点保留。
- 重新开机并登录 Windows 后：任务设置 `StartWhenAvailable`，自动从断点恢复；当前本地模式不承诺在用户完全未登录 Windows 时运行。
- 断电发生在数据库事务中间时，该事务回滚，最近一次已提交游标仍是恢复依据。

## 13. 前台页面范围

### 13.1 机会首页

- 统计：合格项目、24 小时新增、凸性线索、活跃项目、数据受限、最后成功时间。
- “今天先看”最多 8 个真实项目；只要硬门槛通过数大于 0，首页不得为空。
- 不纵向铺开所有分类，不用总分当标题。

### 13.2 全部机会

- 默认“全部”，标签为：全部、凸性线索、活跃项目、新发观察、持续观察、数据受限。
- 20 条/页，有明确页码；支持年龄段、A/B/C、链、产品证据和数据状态筛选。
- 进入详情再返回时恢复标签、筛选、排序、页码和滚动位置。

### 13.3 重要变化

每条变化必须用普通语言回答五件事：发生了什么、之前是什么、现在是什么、为什么影响判断、数据到什么时候。只收录会改变 T0、分类、前台资格、产品证据、五种状态、因子方向、数据可信度或第 91 天退出的事件；普通行情流水不进入。

### 13.4 我们如何判断

用真实示例解释 T0、A/B/C/D、宽硬门槛、凸性线索、活跃项目、贝叶斯分数、来源失败和程序边界。不得只展示术语或公式。

### 13.5 项目详情

首屏回答：为什么进入、T0 与覆盖范围、A/B/C、当前状态、产品证据、主要支持、主要风险、数据时间。完整因子、来源、反证和历史按需展开。

## 14. 前后台数据与失败边界

- C2.1 建议新增独立的 `data/c2.1-pipeline.db` 保存候选归并、T0、分类、日指标、证据路径、来源状态和增量游标；`data/convexity.db` 在 C2.1 首版继续只读，不新增业务表或迁移。
- Gate 0 的 5,922,807 条原始创建事件继续保留在已验收分片文件中，不整批复制进主库。C2.1 只保存可追溯文件位置、哈希、处理游标和归并后的资产结果。
- 前台读取由 C2.1 流水线原子生成的新快照；回滚时可恢复 C2.0 页面和旧快照，不需要回滚或覆盖主数据库。
- 前台只显示对判断的影响、受影响字段和最后成功时间；不显示密钥、额度账户、响应正文、任务 ID、游标或重试按钮。
- 后台保留来源、请求状态、额度、重置时间、游标、分片、重试、公式版本、历史输入和对象级影响。
- 构建失败继续使用上一份完整快照，并在前台显示数据延迟；不得发布半份快照。
- `no_data`、`quota_limited`、`source_failure`、`unsupported`、`configuration_missing`、`program_failure` 必须分别保存。
- 来源失败字段不写 0、不触发项目基本面下降；额度恢复后自动补采和复算，不需要人工内容确认。

## 15. 程序能力上限

| 程序可以做到 | 程序不能做到 |
|---|---|
| 在六链已登记协议范围发现和续扫 | 证明全市场零遗漏 |
| 保存目前查到的最早公开流通证据并向前修正 | 证明它一定是全球真实首次流通 |
| 自动归并明确的旧资产、包装、迁移和桥接关系 | 识别所有隐蔽关联、代持和复杂经济连续性 |
| 通过项目证据排除大量只有代币的对象 | 完全排除伪装 GitHub 的 Meme 或骗局 |
| 观察历史买卖、流动性和公开权限风险 | 保证未来一定能卖出、不会抽池或没有未知后门 |
| 统计链上地址和可检测的关联模式 | 把地址准确等同真实用户，识别所有刷量与女巫 |
| 根据冻结规则形成凸性线索和活跃项目 | 证明项目靠谱、市场低估、未来成功或上涨 |
| 动态更新证据分与可信度 | 在没有时间外结果前证明算法越来越准 |

产品继续不生成建仓、仓位、买卖点，不连接钱包，不自动交易。

## 16. 一个版本内的三个内部里程碑

### M1 数据生产化

- 导入 Gate 0 正式结果并续接增量游标。
- 完成资产归并、旧币新池排除、T0 证据和基础来源状态。
- 验证不会重跑已完成 90 天区间。

### M2 规则与证据

- 完成 A/B/C/D、宽硬门槛、产品证据、五因子输入、强/弱线索、可信度和重要变化。
- 用固定真实样本和合成边界样本验证同输入可复算、缺失不写零、年轻项目不受时间权重。

### M3 前后台与发布

- 接入四个前台页面、项目详情和后台更新/来源/进度页面。
- 完成手动更新、可选自动频率、原子快照、恢复和桌面真实路径验收。
- C2.1 只支持现有 Windows 桌面产品；验收 1180×760 默认窗口和 1440×900 或最大化窗口。不开发手机端、平板端或移动端响应式布局，不执行 375、390、768 等移动视口验收。

三个里程碑属于同一个 C2.1 开发范围，不要求用户逐段重新授权；但任何范围变化仍需用户确认。只有 M1—M3 和最终独立验收全部通过后才发布，不发布半成品前台。

## 17. 首版明确不做

- 不扩展 Gate 0 未确认的 18 个 EVM 标签。
- 不承诺 CEX 全量发现、私域发行或未接入链。
- 不把钱包地址数写成用户数。
- 不用大模型生成或修补缺失数据、T0、项目关系、分数或结论。
- 不因接口额度不足随机抽样、只追热门项目或改变算法权重。
- 不建立逐项目人工通过、退回、确认和发布流程。
- 不输出投资动作、仓位、价格预测或收益概率。
- 不开发手机端、平板端、移动端响应式页面或移动端发布包。

## 18. 用户已确认并冻结的产品选择

用户于 2026-08-10 已确认：

1. 前台采用五状态，单独保留“活跃项目”，同意本稿分类设定。
2. 日常增量采集同时支持后台手动和自动方式，采用本稿的统一隐藏运行、断点和恢复方案。
3. 同意本稿凸性线索设计：至少两条强证据路径，其中一条必须是交易与流动性，综合分不能单独触发。
4. C2.1 当前完全不考虑移动端适配，只交付 Windows 桌面产品。

四条强证据路径的美元护栏、百分位、异常阈值、缺失处理、进入/退出防抖和固定回归样本已经写入本需求、正式规则配置和回归清单。用户已明确冻结 C2.1；实现只能追溯到需求锁所列正式文件，不得临场改变规则。

## 19. 更新机制的冻结验收底线

正式验收必须至少证明：

1. 同一冻结输入分别由“立即更新”和自动任务运行，数据库结果、项目状态和快照哈希一致。
2. 正式桌面路径执行手动、自动、恢复和重试时，控制台黑框出现次数均为 0。
3. 更新中关闭产品窗口和 Codex 后，独立任务仍继续并完成。
4. 在固定分片中模拟断网、超时、429、5xx、进程终止和电脑重启，恢复后从最后已提交游标继续；已完成分片的新增网络请求为 0。
5. 同时触发手动和自动任务时只有一个写入者，第二次触发不产生第二进程或重复数据。
6. 数据库事务失败、快照构建失败或来源长期中断时，上一份完整前台快照仍可用，未提交游标不前进。
7. `no_data`、`quota_limited`、`source_failure`、`unsupported`、`configuration_missing`、`program_failure` 分别进入后台和前台影响说明，不统一写成“资料不足”。
8. Windows 未登录时不运行的边界在后台明确展示，不能把“开机”误写成“已经后台更新”。
