# C2.2 候选生产化覆盖修复：实施与终验交接

状态：正式冻结，等待开发授权

## 1. 实施顺序

1. 读取本修复需求锁和原 C2.2/C2.1 冻结文件，核验全部哈希。
2. 记录当前数据库、任务、暂停、频率、调度器、快照和真实桌面基线。
3. 先在数据库副本上实现本地基础扫描、状态迁移和分母对账测试。
4. 实现双队列、六链轮转、分片、原子检查点、单实例和恢复；使用固定小分片做中断测试。
5. 实现逐层接口调用、复查频率、来源状态和跟踪资格批次。
6. 调整凸性跟踪读取边界：允许已完成批次中的 D/待身份资产在后台跟踪，但公开快照继续排除。
7. 在“90 天新币筛选”页面增加“历史候选基础扫描”独立区域，不改凸性跟踪页面职责。
8. 完成数据库副本、全量回归、真实桌面和独立终验后，才可发布程序。
9. 发布程序不等于启动正式 459 万扫描；正式启动需要用户另行明确授权。

## 2. 禁止事项

- 不修改原 C2.2 需求锁及所列冻结文件；
- 不修改 C2.1 数值门槛、贝叶斯、P60/P70、强路径和报价护栏；
- 不重跑 Gate 0，不从区块链重新生成 90 天历史；
- 不新增第二个长期调度器；
- 不对全部候选无差别调用所有接口；
- 不让 D/待身份资产进入公开前台；
- 不用名称、Symbol、Meme 文案或大模型决定身份和排除；
- 不在没有断点和进度时启动长任务；
- 不用正式数据库进行破坏性或写入型验收；
- 不借修复删除已有功能、历史页面或回滚资源。

## 3. 实现报告必须说明

- 每个修改文件及其需求追溯；
- 修复前后实际漏斗分母；
- 本地扫描状态和排除原因分布；
- 双队列、六链轮转和恢复证据；
- 外部接口调用量、来源状态和冷却；
- D/待身份后台跟踪与公开排除对账；
- 数据库、快照、桌面和调度器验证；
- 尚未启动正式历史扫描的明确声明。

## 4. 独立终验责任

终验必须从需求锁和原始数据库副本重新验证，不相信实现报告本身。发现冻结范围缺陷可直接修复并重验；任何规则范围变化、公开资格变化、付费来源、新链、新调度器或正式长任务启动都需要用户另行授权。
