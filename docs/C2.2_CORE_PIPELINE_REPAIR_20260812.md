# C2.2 核心筛选—凸性跟踪链路纠错发布

发布日期：2026-08-12（Asia/Shanghai）

> 纠正说明：本文件记录的上一轮修复只解决了“谁能进入凸性跟踪”，但当时没有证明约 1.5 万个历史市场候选已经完整交给 T0/新币第一关。该缺口已由 `docs/C2.2_T0_FIRST_GATE_HANDOFF_REPAIR_20260812.md` 继续修复并取代本文件的交接完成结论。

## 大白话结论

历史底座确认“市场上确实出现过”的代币后，不能直接交给凸性跟踪。正确顺序已经固定为：

`历史市场候选 → T0、身份、A/B/C/D、产品证据和宽硬门槛核验 → 只把通过的 A/B/C 交给凸性跟踪 → 前台展示`

D 类、身份未完成或宽硬门槛未通过的对象继续留在第一关后台，不再进入凸性跟踪，也不生成前台项目详情。

## 本次确认的根因

1. 历史市场扫描拿到了代币名称、符号、网站和更早的真实池时间，但旧保存逻辑没有把这些输入交给第一关；没有旧项目 ID 的全新项目也被错误挡住。
2. 历史候选批次在第一关核验完成前就被标成“资格完成”，使第二关能提前读取尚未核验的对象。
3. 凸性跟踪读取了兼容旧结构的宽泛 `tracking_eligible` 字段，把 D 类和身份未确认对象也当成第二关输入。
4. C2.1 快照允许没有候选生产记录的旧评估结果绕过第一关；同时两条链使用了不同的备用 `assetId`，造成前后台数量重复或不一致。

## 已完成的修复

- 市场确认结果保留名称、符号、官网、最早真实池时间和 T0 输入。
- 新项目不再因为没有旧 `projectId` 被挡住；可以以稳定 `assetId` 和 C 类关系进入第一关。
- 每个历史分片必须完成第一关处理后，资格批次才能原子地变为 `completed`。
- 凸性跟踪只读取“已完成资格批次＋宽硬门槛通过＋A/B/C”的对象。
- C2.1/C2.2 快照统一使用候选生产记录中的稳定 `assetId`；没有生产记录的旧评估不再进入正式快照。
- 保留旧 `tracking_eligible` 字段只为数据库兼容；它不再等同于“已进入凸性跟踪”。
- 历史扫描继续使用既有分片、游标、单实例锁和断点恢复，不重头扫描。

## 固定测试优先级

测试顺序只以 `docs/TEST_PRIORITY_POLICY.json` 为准：

1. Tier 0：核心业务链。候选必须先过第一关，只有通过的 A/B/C 才能进入凸性跟踪和前台。
2. Tier 1：数据与数量合同。第一关、交接、第二关、前台数量和稳定 ID 必须一致。
3. Tier 2：真实桌面主路径。正式入口、单实例、核心页面和服务连续性必须通过。
4. Tier 3：边缘功能。只有前三层通过后才扩散检查；边缘测试数量不能抵消核心失败。

任何更高优先级测试失败时必须立即停止发布，先修核心问题，不再用大量低优先级通过项证明版本可用。
