# C2.4 现役调度与集合对账热修复

## 目标与成功标准

- 修复 Windows 调度器显示返回 0，但内部“新币筛选”和“凸性跟踪”因 C2.4 集合对账失败的现役问题。
- 同一轮合同变化必须完成本地第一关复核，已物化的第一关积压清空后才发布 C2.4 原子快照。
- 第 91 天以后才首次达到公开条件的项目不得冒充“90 天后持续跟踪”。
- Windows 任务结果必须传递 Python 真实退出码。

## 复现与根因

| 现象 | 根因 | 影响 |
|---|---|---|
| 每轮最多把 500 个旧对象重新置为待复核 | 合同刷新只入队，候选生产每轮只补 50 个旧积压 | 积压在计划任务重试中持续扩大 |
| C2.4 快照在本地第一关尚未完成时就对账 | “历史已跟踪”与“本轮已通过第一关”暂时不同步 | `newTrackedNotQueued` 阻止原子发布 |
| 2 个项目超过 90 天后才首次公开 | 公开历史入库前没有验证“曾在 0—90 天完成两关并公开” | 生命周期状态违反 C2.4 冻结合同 |
| Windows 最近结果为 0 | VBS 等待 Python 后未返回子进程退出码 | Windows 成功表象掩盖内部失败 |

2026-08-14 正式库只读证据：第一关已物化待复核 864 条；对账差异 235 条，其中 233 条是当前仍通过但尚未复核完成，2 条是超过 90 天后才首次公开的无效持续跟踪状态。

## 非范围

- 不修改 C2.4 筛选门槛、贝叶斯算法、六链来源或 UI。
- 不修改 C2.5 冻结文件。
- 不重跑 459 万历史底座、Gate 0 或任何全量外部采集。
- 不复制或覆盖正式数据库，不改用户更新频率与暂停设置。

## 发布与回滚边界

本文档属于开发候选证据，不代表已发布。因修复涉及现役调度、数据库状态和 C2.4 原子快照，必须对固定候选提交执行独立终验，获得用户发布授权后才能合并正式 `main`。
