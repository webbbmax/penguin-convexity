# C1.9 前后台分离体验审计

状态：冻结依据；审计本身不属于需求哈希锁，产品仍未编码  
审计日期：2026-08-03  
审计方式：桌面入口真实点击、页面可见内容检查、导航与运行状态代码只读核对

## 1. 结论

当前问题不是单个栏目命名不佳，而是产品层级没有真正分开：桌面壳把机会中心、项目详情和工作台并列；机会中心又复用工作台页面；工作台同时承担读结论、运行任务、看原始数据和模型工具。结果是普通用户看到后台语言，管理者又要在大量研究内容中寻找系统状态。

C1.9 必须先重建前后台产品边界，再做页面、用语、UI和交互。仅在现有页面上换颜色或改标题不能解决问题。

## 2. 已确认的产品边界

- 凸性机会中心是前台展示产品，面向不懂程序、不负责维护系统的普通用户，未来可能独立上线给大众。
- 凸性工作台是后台管理产品，面向产品维护者和研究运营人员，负责更新、任务、来源、证据、异常、配置和运行状态。
- 项目详情是上下文页面，不是顶级产品栏目。用户从结论、机会卡片、变化或项目列表进入，返回后回到原入口、原筛选、原页码和原滚动位置。
- 前台只解释“现在怎么看、为什么、发生了什么、风险是什么、何时再看”；后台才解释“哪个任务、哪个来源、运行到哪一步、为什么失败、怎么恢复”。
- C1.9 只做体验重构和为体验服务的运行状态可见性，不新增研究数据主干，不修改评分、动作、L0-L5或研究规则。

## 3. 真实体验中发现的核心问题

### 3.1 三层导航互相打架

当前同时存在：

1. 桌面左侧导航：机会中心、项目详情、工作台。
2. 机会中心横向导航：当前结论、行动条件与缺口、重要变化、催化与交易闭环、项目类别、跟踪进度、项目库。
3. 工作台横向导航与“系统与模型”菜单：工作台、项目队列、机器发现、弱线索、更新中心、信源状态、原始证据、催化路径以及 16 个高级工具。

普通用户无法判断自己是在看产品结论、项目资料还是后台管理；同一页面也可能同时显示前台标题、后台导航和桌面壳标题。

### 3.2 前台直接暴露后台职责和术语

机会中心首页直接出现“系统工作与需要我处理”“负责人：系统自动核验”“每小时到期检查”“打开工作台”等维护语义。行动缺口页继续展示负责人、系统下一步和检查排期；这些信息对后台有用，但不应成为大众前台的主要阅读内容。

前台还直接展示“项目主体待核验”“价值传导待闭环”“规则重算”“分层未变”等研究或系统语言。用户需要的是自然解释，例如“还无法确认项目和代币的官方关系”“尚未证明这件事会给该资产带来价值”。

### 3.3 前台页面实际复用了后台壳

从机会中心进入“重要变化”和“催化路径”后，页面顶部变成“凸性工作台”导航，底部也标注“凸性工作台 C1.7”。这证明当前前后台不是视觉相似，而是路由和页面职责本身混用。

### 3.4 项目详情被错误提升为产品栏目

桌面左栏把“项目详情”设为与机会中心、工作台同级，并保存“最近查看的项目”。实际详情只应服务一次上下文阅读。详情页还提供近 600 个项目的超长下拉切换框，既难用，也把详情页再次做成项目管理入口。

### 3.5 前台信息密度仍然偏后台

- 首页“接近行动门槛”一次显示条件计数、首要缺口、负责人和下次检查，普通用户很难先抓住结论。
- “重要变化”默认列出 596 个项目、2,002 条历史记录，并把“分层未变”和“比较基线”作为主要内容；用户需要的真正变化被大量无变化记录淹没。
- “催化交易路径”默认展示全部 596 条路径和系统断点，更像后台排查工具，而不是大众解释页面。
- 多个页面虽然使用分页，但仍以数据库记录为中心组织内容，不是以用户问题为中心组织内容。

### 3.6 工作台入口和工具数量过多

工作台首屏同时出现恢复建议、8 个快捷入口、4 个状态数字、5 步闭环、4 步日常流程、运行明细和近 20 个模型/数据工具。管理者仍需先理解产品历史和数据结构，才能判断今天要处理什么。

### 3.7 全量更新缺少运行中进度

当前运行状态只保存任务开始时间、结束时间、最终消息和最终结果。运行中页面只显示“正在更新”和开始时间；没有：

- 当前阶段；
- 已完成步骤/总步骤；
- 已处理项目或来源数量；
- 最近一次心跳；
- 成功、失败和等待数量；
- 是否正在等待外部来源；
- 是否可能卡住。

因此一次持续 40 分钟到 1 小时的全量更新期间，用户确实无法区分“正常运行、外部来源等待、程序卡住或已经失败”。这不是用户不会使用，而是当前状态模型没有提供足够反馈。

### 3.8 视觉层级缺乏统一设计

- 桌面左栏使用深色渐变、大面积高对比，与当前浅色内容区割裂。
- 前台和后台共用大量相同卡片、粗边框、全大写英文眉题和密集数字，无法通过视觉立即辨认当前产品角色。
- 当前页面多处使用大号衬线标题、多个同等强调按钮和等权信息块，主结论、重要变化与辅助说明没有形成清晰强弱关系。
- iframe 外壳和页面内部各自拥有头部、导航、边框与状态，造成“页面套页面”的视觉负担。
- M1.0、C1.7、C1.8 等版本标签分散在桌面壳、页面标题和页脚。版本是后台维护信息，却持续占用普通用户注意力，也让不同历史版本看起来像仍同时运行。

## 4. 根因判断

1. M1.0 为了快速独立迁移，桌面壳保留了历史三入口结构；迁移保证了独立运行，但没有重建产品角色。
2. C1.8 解决了长滚动和责任说明，却仍把“后台是否自动工作”放进前台，并复用部分工作台页面。
3. 当前页面以历史功能文件为单位导航，而不是以前台用户任务和后台管理任务重新分组。
4. 更新任务只记录开始和结束，前端轮询无法获得中间进度；因此单纯增加加载动画也不能解决状态不透明。

## 5. C1.9 必须解决的 P0

- 前台与后台使用两个独立信息架构和两个独立页面壳，不再复用导航与页脚。
- 删除“项目详情”顶级导航；详情从项目上下文进入和返回。
- 前台不显示来源适配、Watcher、孤儿证据、任务负责人、调度配置、运行日志、重试和模型工具。
- 前台默认只显示真正影响判断的变化；“未变化”和“比较基线”不进入大众变化流。
- 后台首页只回答：系统是否正常、当前是否在运行、异常在哪里、下一步做什么。
- 全量更新运行时必须持续显示阶段、进度、最近心跳、已完成/失败数量和明确状态，不伪造百分比或预计时间。
- 全产品改为浅色、现代、清晰的视觉体系，并建立一致的字体、间距、按钮、状态和强调层级。
- 面向用户可见的版本号只在工作台左侧栏底部固定显示一次；前台、详情、桌面宿主、页眉、页脚和卡片不再展示版本号。

## 6. 本轮未做

- 没有修改任何 HTML、CSS、JavaScript、Python、数据库或调度任务。
- 没有运行全量更新、复核、重试或任何写入业务数据的操作。
- 审计阶段没有修改产品代码；用户随后已冻结 C1.9，当前仍未开始 Luna 实现。
