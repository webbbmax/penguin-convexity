## 3. 更新和恢复怎么运行

- 手动和自动共用同一条隐藏、单实例、可恢复流水线，只写 `data/c2.1-pipeline.db`。
- 没有新建第二个长期任务；原任务 `PenguinConvexity-C1.8-Scheduler` 已迁移到 C2.1 统一入口。
- 用户原配置是自动开启、每天一次，因此 C2.1 保留为每 24 小时启动新一轮。15 分钟只做到期与失败恢复检查，不等于每 15 分钟全量采集。
- 正式入口由 `wscript.exe` 隐藏启动，正常桌面黑框为 0。关闭产品或 Codex 不中断已启动任务；关机/休眠后在下次 Windows 登录时从已提交游标恢复。

## 6. 2026-08-11 真实桌面纠正验收

- 根因一：桌面启动器仍要求 `C2.0` 和旧页面资源，健康的 C2.1 被误判为启动失败。
- 根因二：空 `server.stderr.log` 在 PowerShell 中返回 `Null`，启动器直接调用 `.Trim()`，因此出现用户截图中的弹窗。
- 根因三：桌面服务仍会在启动时执行旧任务恢复和旧快照重建，违反 C2.1 主库只读边界。
- 修复后从正式桌面快捷方式冷启动，健康状态为 `C2.1/success`，桌面实例数为 1，重复双击不生成第二窗口，关闭后位置与尺寸可恢复。
- 真实首页显示 12 个前台合格项目、6 个活跃项目、6 个持续观察、0 个凸性线索，不是空壳或启动占位页。
- 主库冷启动前后哈希一致，`runs` 47/47、`run_errors` 10/10、守护恢复记录 5/5，没有再发生启动写入。
- 受影响验收重跑通过：C2.1 独立验收 7/7、发布检查通过、真实 HTTP 路由 31/31、C1.9 前后台边界回归通过；完整 Python 测试第一轮暴露 3 个旧启动契约断言，修正后第二轮 75/75 通过。

- 当前 12 个前台项目全部是 C 类“项目关系未确认”，8 个只有 GitHub 代码证据，4 个有结构化业务数据。程序能分层，但不能因此证明项目靠谱。
