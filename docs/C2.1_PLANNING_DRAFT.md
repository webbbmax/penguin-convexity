# 企鹅投研-凸性｜C2.1 规划与产品设计稿

状态：Gate 0 前历史规划草案；仅保留形成过程，不得作为实现依据。冻结候选以 `docs/C2.1_FREEZE_DRAFT.md` 所列文件为准  
版本：C2.1「90天新发项目全量前台与动态证据分层」  
规划时间：2026-08-04（Asia/Shanghai）  
历史形成模型：`gpt-5.6-sol`；该记录不再构成模型门禁

## 1. 版本结论

C2.1 是新路线的第一个纵向可用版本，不再把“前台资格”“凸性线索”“高可信判断”混成同一道门槛。

本版本的产品承诺是：

> 在已接入链、市场和来源的可发现范围内，持续发现真实 T0 不超过 90 天的代币；全部通过宽硬门槛的 A/B/C 类对象进入前台；程序根据产品证据、真实发币历史、五因子变化和数据状态进行分层，不以某个综合分数决定项目是否可见。

本版本不能承诺：覆盖全市场、完全排除伪装 Meme、认证项目靠谱、证明市场低估、预测上涨或生成投资动作。

## 2. 本版本修正的核心问题

C2.0 的真实状态是项目很多、前台有效信号为零。主要原因不是页面加载失败，而是旧设计把高完整度研究结论当成前台入场券。

C2.1 固定采用以下产品原则：

1. 宽进场：硬门槛只排除明确不合格、只有代币且无项目证据、无法交易或存在硬风险的对象。
2. 全量可见：全部通过硬门槛的对象都能在前台“全部机会”查到。
3. 分层解释：线索形成与否决定状态和理由，不决定是否消失。
4. 分数内用：动态贝叶斯分数只用于排序、变化监控和校准，不作为前台“凸性线索”标签的单一门槛。
5. 真实历史：观察从真实 T0 回溯，不从程序首次收录开始。
6. 年轻不扣分：尚未发生的日期不算缺失，也不额外奖励年轻项目。
7. 零人工项目复核：生产链不建立人工通过、退回或发布确认。

## 3. 对象范围与生命周期

### 3.1 T0 与 90 天窗口

- T0 继续定义为代币第一次允许普通公众实际取得并可转让或交易的最早可验证时间。
- 0—30 天和 31—90 天只用于筛选、解释和直接日期排序。
- 第 91 天自动退出新发前台，进入历史对照库。
- 年龄权重、年龄分、新鲜度分均为 0。
- `firstSeenAt` 只衡量程序发现延迟，不得参与年龄和观察历史计算。

### 3.2 A/B/C/D

- A：新项目新币，可进入前台。
- B：老项目新币，可进入前台，固定标记“老项目新资产”。
- C：项目关系未确认，可进入前台，固定标记“项目关系未确认”。
- D：只有代币，未建立项目身份，只留后台。

## 4. 宽硬门槛

对象同时满足以下条件才进入前台：

1. T0 已核验且 `0≤ageDays≤90`。
2. 属于 A、B 或 C。
3. 代币合约、网络和至少一个公开交易池身份一致。
4. 链上观察到真实买入与真实卖出；这只证明历史交易发生，不保证未来一定可卖。
5. 未发现明确不可卖、冻结、黑名单、异常税费、身份冲突等硬阻断。
6. 至少具有一类可追溯项目证据：GitHub、产品合约、结构化业务数据、已执行代币功能或带链上使用的产品入口。

以下不再是前台硬门槛：

- 观察满 14 天。
- 五因子全部可计算。
- 综合证据分达到固定值。
- 已形成凸性线索。
- 已取得第二类产品证据。

## 5. GitHub 作为首版产品证据

### 5.1 准入规则

官方 GitHub 仓库可以单独满足“至少一类项目证据”，但必须：

- 能从官方项目入口、官方组织资料或其他可复现身份链建立项目归属。
- 仓库非空、未归档，存在代码文件和提交记录。
- 保存是否 Fork、主要语言、提交数、贡献者数、最近提交时间和身份来源。
- Fork 只有在项目仓库存在可验证的自有提交时才计入。

首版不以 Star、Contributor 数量或必须存在链上使用作为 GitHub 硬门槛，避免再次把真实早期项目全部挡住。

### 5.2 前台表达

GitHub-only 项目固定显示：

> 目前仅确认代码仓库，尚未确认产品部署、业务数据或链上使用。

不得写成“产品已验证”或“基本面已确认”。

### 5.3 后续是否收紧

本版本只采集并展示以下机器指标，不预设收紧结论：

- GitHub-only 项目数及占全部前台项目比例。
- GitHub-only 项目在第 7、14、30 天获得第二类产品证据的比例。
- 空仓库、归档仓库、无自有提交 Fork、仅文档/静态站点仓库的比例。
- GitHub-only 项目触发硬风险、数据中断或第 91 天退出的比例。

只有真实分布证明 GitHub-only 污染显著时，才由后续版本收紧；不得在 C2.1 实现中临场增加未冻结门槛。

## 6. 真实历史回溯与短历史补偿

### 6.1 观察起点

- 所有历史字段从真实 T0 对应的链上时间开始回溯。
- 项目在发币第 10 天被发现，成功回溯 10 天时，观察历史为 10 天，不是 1 天。
- 无法回溯的日期标记 `backfill_gap`，不能用程序收录后的快照填充。
- 历史价格、流动性或交易池状态仅在支持的来源和 DEX 协议范围内重建。

### 6.2 可观察窗口补偿

`effectiveWindowDays = min(ageDays + 1, 14)`。

- 活跃比例使用“有效活动日 / effectiveWindowDays”。
- 日均成交、日均地址和日均调用使用真实可观察日作分母。
- 发布不足 14 天的项目与相同发行日龄的冻结历史基准比较。
- 尚未发生的日期不计零、不降低证据分，也不重新分配到其他因子。
- 历史短会降低独立可信度，但不会阻止项目进入前台。
- 满 14 天后切换到完整前 7 日/后 7 日与持续性模型。

这不是时间加分；相同数据下，年轻项目不会因为更年轻自动获得更高评价。

## 7. 动态贝叶斯五因子与可信度

五因子继续使用：

| 因子 | 内部权重 | 主要内容 |
|---|---:|---|
| D 交易需求 | 25% | 独立交易地址、重复参与、活动连续性、买卖参与结构 |
| L 流动性与退出 | 25% | 流动性/估值、估算滑点、流动性保留、价格冲击 |
| S 持币与供应 | 20% | 头部集中度、HHI、非尘埃持币地址、Mint/Burn 与净供应 |
| G 活动与估值关系 | 15% | 成交额/市值或 FDV、地址和交易增长相对估值变化 |
| Q 稳定性与异常集中 | 15% | 单日成交集中、地址集中、大额成交集中、价格和流动性异常 |

固定规则：

- 因子与总分只进入后台规则快照和前台排序理由，不在前台显示“多少分等于凸性线索”。
- 缺失数据不写 0，不跨因子重分配权重。
- 旧证据可按 14 天半衰期降低影响；这是证据时效，不是项目年龄权重。
- 同一输入、同一模型版本必须得到相同结果。
- 独立可信度只衡量覆盖、时效、历史长度和同定义来源一致性，不给证据分加分。

## 8. 前台四状态

所有通过硬门槛的项目必须且只能进入一个状态：

1. `data_limited` 数据受限：关键接口额度耗尽、来源故障、回溯断档或数据超时影响当前判断。
2. `evidence_formed` 形成线索：至少满足一条冻结的使用扩张、流动性形成、代币功能或供需结构证据路径。
3. `early_observation` 新发观察：真实历史不足 14 天，尚未形成证据路径。
4. `continuous_observation` 持续观察：真实历史已满 14 天，硬门槛仍通过但尚未形成证据路径。

状态优先顺序固定为：数据受限 > 形成线索 > 新发观察 > 持续观察。

“形成线索”由具体证据路径决定，不由综合总分单独决定。路径的具体数值阈值只在 Gate 0/影子回放后进入正式冻结文件。

## 9. 页面与信息架构

继续保留四个前台导航，不新增第五个顶级栏目：

### 9.1 机会首页

- 首屏显示通过硬门槛总数、最近 24 小时新增、形成线索、数据受限和最后成功更新时间。
- 只显示“今天先看”最多 8 个项目，以及四状态计数入口。
- 当硬门槛通过数大于 0 时，首页项目卡不得为 0。
- 当硬门槛通过数为 0 时，显示发现数、被各硬门槛淘汰数和来源失败数，不用模板补位。

### 9.2 全部机会

- 展示全部通过硬门槛项目，默认“全部”。
- 标签：全部、形成线索、新发观察、持续观察、数据受限。
- 20 条/页，有明确页码，不使用无限滚动。
- 支持年龄段、A/B/C、网络、产品证据类型、流动性、数据状态与更新时间筛选。
- 返回详情后恢复标签、筛选、页码、排序和滚动位置。

### 9.3 重要变化

只展示会改变以下任一项的变化：硬门槛、产品证据、四状态、五因子方向、数据可信度、来源额度状态或第 91 天退出。普通行情流水不单独占据页面。

### 9.4 我们如何判断

解释宽硬门槛、GitHub-only、四状态、五因子内用、真实 T0 回溯、短历史补偿、来源额度反馈、程序边界和不能据此得出的结论。

### 9.5 项目详情

首屏固定回答：为什么进入、当前状态、产品证据、真实历史长度、主要支持、主要风险、数据时间。完整因子、来源和历史渐进展开。

## 10. 接口额度与来源失败

前台只显示对用户判断的影响，后台显示接口、额度、重置时间、响应码、重试和受影响对象。

固定处理：

- 额度耗尽不得归因为项目资料不足。
- 失败字段不写 0，不触发项目基本分下降。
- 保留上次有效值并显示过期状态；超过字段 SLA 后进入 `data_limited`。
- 额度恢复后自动补采、复算和恢复状态，不需要人工确认。
- 额度不足只能降低高成本字段频率、缩短非必要回溯或明确缩小支持范围；不能改权重、放宽硬风险或随机抽样。

## 11. 数据与工程范围

C2.1 允许新增本项目内的业务表、字段、索引、快照和迁移，但必须：

- 正式变更前备份 `data/convexity.db`。
- 不覆盖 C2.0 原始历史、现有评分、动作或 L0—L5。
- 新旧前台快照可并行生成并可回滚。
- 所有密钥继续只从环境读取，不进入代码、文档、数据库、快照或日志。
- 不读取 RWA，不依赖旧整合项目或旧凸性源目录。

## 12. UI 与 UX 进化

### UI

- 首页使用一条紧凑统计带和一组不超过 8 张的“今天先看”卡，不堆四个长列表。
- 全部机会使用状态标签、20 条分页和紧凑项目行；详情再展开完整证据。
- GitHub-only、关系未确认、数据受限使用不同且不带褒义的视觉标签。
- 数据时间、历史覆盖与来源延迟置于结论附近，不藏在页尾。

### UX

- 用户 30 秒内知道前台共有多少合格项目、哪些刚出现、哪些形成线索、哪些因数据中断暂缓判断。
- 用户 3 分钟内核验任一项目为什么进入、证据来自哪里、真实历史从何时开始和为什么尚未形成线索。
- 筛选、分页、详情返回、键盘焦点和已支持桌面窗口保持一致。

## 13. 成功指标与护栏

### 三个主指标

1. 前台资格可见率：前台可查询的硬门槛通过项目数 / 硬门槛通过项目总数，目标 100%。
2. 前台 T0 可追溯率：具有可复现 T0 事件、来源和身份的前台项目数 / 前台项目数，目标 100%。
3. 状态可解释率：具有状态原因、支持证据、主要缺口和数据时间的前台项目数 / 前台项目数，目标 100%。

### 关键驱动指标

- GitHub-only 占比与第 7/14/30 天第二证据转化率。
- 真实 T0 回溯覆盖率和 backfill gap 分布。
- 五因子可计算覆盖率与独立可信度分布。
- 接口额度消耗、来源失败、超时项目和自动恢复时间。

### 不可突破护栏

- 硬门槛通过却被前台静默遗漏：0。
- D 类、T0 未核验、第 91 天后对象进入前台：0。
- 综合分数被写成凸性线索唯一理由：0。
- 尚未发生日期被计为缺失或零分：0。
- 程序收录时间冒充真实历史起点：0。
- 接口额度耗尽被写成项目资料不足：0。
- 真实零结果被模板填充：0。
- 前台无限滚动：0。
- 自动投资动作、仓位或交易：0。
