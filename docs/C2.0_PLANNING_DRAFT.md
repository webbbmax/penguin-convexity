## 1. 版本结论

建议下一版本定义为：

**C2.0 机会信号质量与可解释决策**

最高优先级不是继续增加项目数量、来源数量或后台页面，而是把现有 600 个项目和持续变化转化成普通用户能够快速理解的少量有效信号：现在什么最值得看、为什么值得看、发生了什么、距离行动还差什么、下一次什么变化会改变判断。

C1.9 已解决前后台边界、页面层级和基础交互；C2.0 要解决前台真正的产品价值密度，以及后台如何持续提高这份价值密度。

## 2. 规划依据

2026-08-03 对当前真实页面进行只读体验后，确认以下问题：

1. 首页显示普通建仓 0、极限试仓 0、只观察 600。真实零结果可以成立，但“离行动最近”的前五个项目仍大量使用“事实仍在积累”“风险与交易条件仍需继续确认”等相同表述，无法说明为什么它们比其他 595 个项目更值得先看。
2. “全部机会”当前有 30 页，大量卡片重复“代币价值捕获路径尚未核验”“最大风险：尚未确认”。用户可以浏览，但难以比较项目之间真正不同的缺口、风险和点火条件。
3. “重要变化”当前有 84 页，首屏多数是“交易状态从尚未确认变为受限/已核验”的横向变化，且重复使用“本次为横向变化”。变化数量已经得到分页控制，但信息噪声和阅读优先级仍未解决。
4. 个别变化显示流动性数值但缺少币种或计量口径。数字存在不等于普通用户能够判断其意义。
5. 后台能够看到任务、来源和运行状态，但缺少“哪些共同缺口导致 600 个项目全部停留在只观察、先解决什么最能提高前台判断质量”的产品质量视图。

因此，下一版必须从“能展示全部信息”升级为“能压缩信息并解释优先级”。

## 3. 产品定位

### 前台：凸性机会中心

前台不是项目数据库，也不是后台任务结果的镜像。它只回答普通用户五个问题：

1. 现在有没有满足行动门槛的机会？
2. 如果没有，哪些项目最值得继续关注？
3. 为什么它们比其他项目更接近行动？
4. 最近发生的变化会改善判断、收紧判断，还是只是普通波动？
5. 下一项什么事实出现时，当前判断才可能改变？

### 后台：凸性工作台

后台负责保证前台结论可信、具体、及时。它需要回答维护者五个问题：

1. 哪些数据质量问题正在影响前台判断？
2. 哪些共性缺口阻塞的项目最多？
3. 哪些变化被判为噪声、重复或缺少单位？
4. 系统能自动补齐什么，哪些事项需要人工确认？
5. 先处理哪一项最能提高前台有效信号比例？

## 4. C2.0 主功能框架

### C2.0-01 前台阅读优先级层

建立独立于投资动作的“阅读优先级”。它只决定用户先看什么，不修改普通建仓、极限试仓、只观察、反身性管理或失效/排除，也不替代 L0-L5、风险、剩余凸性、交易性或点火距离。

前台按三层组织：

- **现在必须看**：出现可能改变动作、风险或失效判断的新事实。
- **值得继续看**：出现具体进展，但尚未跨越行动门槛。
- **保持观察**：没有重要变化，留在全部机会目录，不占用首页注意力。

首页“最值得看”最多展示 5 个项目。每个项目必须有一条项目专属理由、一条当前首要缺口、一条下一触发条件和证据时间；没有符合条件的项目时明确显示“本期没有需要优先阅读的新机会”，不得用通用模板凑满 5 个。

### C2.0-02 变化降噪与影响解释

- 同一项目、同一轮运行、同一字段的重复变化合并为一条。
- 同一项目短时间内的连续变化合并成事件链，默认只显示最终状态和净变化，可展开查看过程。
- 变化必须标明对当前判断的影响：可能改善、可能收紧、尚不改变判断。
- “尚不改变判断”默认不进入首页，只保留在“重要变化”的次级筛选或项目详情历史中。
- 数值变化必须显示单位、时间范围和比较基准；缺少口径时不在前台渲染成精确数字。
- 每条变化都要说明“为什么重要”或“为什么暂时不重要”，不再只显示字段由 A 变为 B。

### C2.0-03 项目专属结论生成

把重复模板改为项目专属的五段式摘要：

1. 当前动作。
2. 当前最强支持事实。
3. 当前最大阻断或最大风险。
4. 下一触发条件。
5. 失效条件与证据时间。

当数据不足以形成项目专属摘要时，前台明确写“资料不足，暂不进入优先展示”，后台同时登记具体缺口。不得把“尚未确认”作为没有上下文的通用最大风险。

### C2.0-04 后台判断质量中心

在工作台新增“判断质量”视图，不新增新的前后台混合页面。核心内容：

- 项目覆盖漏斗：主体身份、可购买资产、价值捕获、最大亏损、交易与退出、点火条件、证据时效分别有多少项目已闭环、待系统处理、待人工确认。
- 共性阻断排行：按影响项目数和对前台结论的影响排序，不按技术任务数量排序。
- 前台质量指标：项目专属摘要覆盖率、通用模板占比、变化合并率、缺少单位数量、过期证据数量、首页有效信号数量。
- 闭环队列：明确负责人、系统下一步、预计复查时间、成功/部分完成/失败原因。
- 质量回溯：能够从前台一条结论回到证据、来源、转换过程和最近一次规则运行，但不把这些后台信息泄露到前台。

### C2.0-05 排序与空结果诚实表达

- “离行动最近”必须由已经冻结的独立维度组合产生可解释排序，不新增或暗改投资评分。
- 排序理由必须能够被普通语言复述，并能回指实际字段。
- 真实 0 个可行动项目时继续诚实显示 0；但要同时说明最常见的前三类阻断，以及是否出现值得优先阅读的新变化。
- 不为了让页面看起来热闹而降低行动门槛、伪造候选或把横向变化包装成机会。

## 5. 本版本 UI 进化包

每个版本必须在主功能之外包含一组明确的 UI 改进。C2.0 的 UI 重点是“视觉上直接看出重要程度”。

1. 首页从同权卡片改为三级视觉权重：当前结论最强、优先信号次强、状态与时间弱化。
2. “最值得看”使用有限卡片，不够 5 个不补齐；卡片首行突出变化和影响，不重复显示动作名称。
3. “重要变化”改为按项目聚合的时间线；同一项目连续变化折叠，展开后再看细节。
4. 数字统一单位、千分位、涨跌方向和时间范围；风险色只用于真实风险或失败，不把普通状态全部染色。
5. 项目详情首屏固定展示五段式摘要，证据链、历史变化和方法说明渐进展开。
6. 后台判断质量中心优先使用可排序表格、漏斗和聚合条，不用大量同权卡片堆满屏幕。
7. 前后台继续使用浅色南极蓝体系；正文、辅助文字、状态标签和警告建立统一字号、对比度与间距层级。
8. 保持 1280×720、1440×900、1920×1080 和 125% 缩放可用；键盘焦点、空状态、加载、部分完成和错误状态必须有独立设计。

## 6. 本版本 UX 进化包

每个版本必须在主功能之外包含一组明确的 UX 改进。C2.0 的 UX 重点是“30 秒得到答案，3 分钟完成核验”。

1. 首次进入首页，30 秒内能够回答：是否可行动、最值得看什么、最大限制是什么、最近什么变了、下一触发是什么。
2. 首页到项目详情只需一次点击；返回后恢复来源、筛选、页码和滚动位置。
3. “重要变化”默认只显示需要优先阅读的变化；用户主动选择后才能展开全部横向变化。
4. 全部机会保留搜索、筛选和分页，并新增可解释的排序理由，不提供无法解释的“综合分”。
5. 前台任何“待核验、待闭环”都说明由系统继续处理还是需要用户行动；普通用户默认不承担数据维护任务。
6. 后台从质量问题直接进入对应项目或来源处理页，处理后回到原筛选位置。
7. 系统不能形成可信结论时显示原因和下次复查时间，不使用无限加载、空白卡片或通用“暂无数据”。

## 7. 验收硬门槛草案

### 前台价值

- 首页最多 5 个优先项目，全部具备项目专属理由、首要缺口、下一触发和证据时间。
- 没有合格项目时显示真实空状态，通用模板补位数量为 0。
- 首页和“重要变化”中，同项目、同轮、同字段重复变化为 0。
- 所有可见数值都有单位或明确标注“口径尚未确认”。
- 抽查至少 30 个项目，普通用户能够区分项目之间不同的阻断原因；无上下文“最大风险：尚未确认”为 0。

### 后台质量

- 判断质量漏斗各分类可以与数据库项目总数对账。
- 每个阻断都能显示影响范围、责任方、下一步、最近执行和预计复查时间。
- 前台结论可以回溯到本项目内证据与来源，不产生孤立展示结论。
- 变化合并前后保留完整原始历史，不删除证据或覆盖事实。

### UI / UX

- 普通用户真实点击测试中，能够在 30 秒内完成五问理解任务。
- 重要变化默认视图不出现无限下拉；每页最多 20 个项目事件链。
- 三级视觉权重在三种桌面视口和 125% 缩放下均清晰可辨。
- 前台不出现任务 ID、Watcher、游标、重试、调度、日志、模型术语或版本号。

### 业务边界

- 核心评分、动作、L0-L5、风险、剩余凸性、交易性、点火距离和生命周期规则文件哈希必须与 C1.9 基线一致。
- 不自动交易，不降低行动门槛，不新增到 RWA、旧整合项目或源项目的运行时引用。
- 原始证据、来源、弱线索、历史变化和恢复备份完整保留。

## 8. 明确不做

- 不新增大批外部数据源，不以项目数量增长作为版本成功指标。
- 不修改评分、结论门槛、动作、L0-L5或投资研究规则。
- 不开发自动交易、账户体系、社区、订阅、支付或公开部署。
- 不重做 C1.9 已发布的前后台导航边界。
- 不把后台质量指标直接搬到普通用户前台。
