# C2.0 机会信号质量与可解释决策 PRD

状态：已冻结，等待 Luna 一次性实现  
冻结授权：用户于 2026-08-03 明确回复“按已确认方案冻结 C2.0”  
当前已发布版本：C1.9；C2.0 尚未编码、尚未发布  
产品名：企鹅投研-凸性

## 1. 版本结论

C2.0 不继续以项目数量、变化数量或后台页面数量作为成功指标。它要把现有项目、证据和横向变化压缩成少量、具体、可解释的前台决策信号，并让后台能够持续回答“哪些共性缺口正在降低判断质量、先处理什么最有效”。

本版本同时交付三类结果：

1. 主功能：阅读优先级、变化事件链、项目专属五段式摘要和后台判断质量中心。
2. UI 进化：重要程度可被直接看见，变化按项目聚合，详情首屏形成稳定摘要，后台由同权卡片改为漏斗与可排序队列。
3. UX 进化：普通用户 30 秒得到答案、3 分钟完成依据核验；维护者从质量问题进入处理页并原路返回。

## 2. 成功标准

### 2.1 普通用户

首次进入机会首页，30 秒内能够回答：

1. 当前有没有满足行动条件的机会；
2. 现在最值得先看哪些项目；
3. 为什么这些项目比其他项目更值得先看；
4. 最近什么变化可能改善、收紧或暂不改变判断；
5. 下一项什么事实出现时，当前判断才可能改变。

任一优先项目都必须具备项目专属理由、首要阻断、下一触发、失效条件和证据时间。合格项目不足 5 个时不补位；没有合格项目时诚实显示真实空状态。

### 2.2 维护者

进入“判断质量”后，30 秒内能够回答：

1. 七类判断环节各有多少项目已闭环、待系统处理、待人工确认；
2. 哪三类共性阻断影响项目最多、对前台影响最大；
3. 项目专属摘要、通用模板、变化合并、缺少单位、过期证据和首页有效信号分别处于什么状态；
4. 每项问题由谁处理、下一步是什么、何时复查；
5. 一条前台结论如何回到本项目内证据、来源、转换过程和最近规则运行。

## 3. 不可变业务边界

C2.0 是解释与展示层版本，不是新的投资体系。

- “现在必须看、值得继续看、保持观察”只表示阅读顺序，不是投资动作、评分、仓位或 L0-L5。
- 不修改普通建仓、极限试仓、只观察、反身性管理、失效/排除五种动作及其门槛。
- 不修改 L0-L5、风险、剩余凸性、交易性、点火距离、价值捕获、生命周期路线或现有评分。
- 不新增“综合分”“阅读分”“信号分”或其他可替代投资判断的数值。
- 不自动交易，不连接钱包，不降低行动门槛，不为页面热闹伪造候选。
- 不修改或删除原始事件、标准事件、证据、溯源、弱线索、历史变化、监控目标和催化路径。
- 不新增大批外部来源、Watcher 主线或新的研究数据能力。
- 不写入或运行时引用 RWA、旧整合项目、源项目；公共 API 共享边界不变。

以下五个核心文件在 C2.0 实现和发布前后必须保持 SHA-256 不变：

- `storage/rulebook-v1.json`
- `storage/state-machine-v1.json`
- `storage/schema.sql`
- `storage/data-dictionary.json`
- `scripts/rule_engine.py`

## 4. 实现架构决策

C2.0 采用“只读派生展示层”，不增加 SQLite 业务表，不改变现有表语义。

### 4.1 权威输入

- 当前项目与候选：`candidate_cases`、`projects`、当前候选快照。
- 当前判断：最新已发布 `machine_conclusions`、`machine_research_scores` 和候选独立维度。
- 支持、反面与时间：`evidence_items`、`evidence_lineage`、原始/标准事件。
- 最大亏损、点火与失效：`convexity_reviews`、`catalyst_trade_paths`。
- 变化：`opportunity_stage_history` 和 `tracking_task_runs.findings_json`。
- 责任与复查：跟踪任务快照、当前任务状态和现有后台处理入口。

### 4.2 新派生输出

- `app/decision-signals-snapshot.js`：只含前台安全字段；不得携带任务 ID、Watcher、游标、日志、内部路径或后台操作。
- `app/decision-quality-snapshot.js`：只供后台“判断质量”使用，保存漏斗、阻断排行、质量指标、闭环队列和溯源链接。
- 两份输出均由 `scripts/build_decision_quality_snapshots.py` 在本地一次构建，使用同一个输入时间点和同一组运行 ID，先写临时文件并校验，再原子替换两个活动快照。

派生快照不是新的事实源。构建失败、对账失败或两份快照时间点不一致时，保留上次有效快照，并在前台显示数据状态、后台显示失败原因；不得输出一半成功、一半旧数据的混合结果。

### 4.3 现有快照关系

- 不删除 `candidate-pool-snapshot.js`、`change-explanations-snapshot.js`、`project-detail-snapshot.js` 或 `tracking-task-snapshot.js`。
- C2.0 派生构建器读取这些现有结果及数据库，只形成解释、排序、合并和质量视图。
- 任何更新写入原始事件后，仍须先完成 Event Schema v2 本地增量规范化，再重建现有快照，最后重建两份 C2.0 派生快照。
- 两份 C2.0 快照重建属于现有七阶段的“跟踪与页面发布”，不新增第八阶段。

## 5. C2.0-01 前台阅读优先级

### 5.1 固定层级

前台只使用三层：

1. **现在必须看**：当前为普通建仓或极限试仓，或最近变化涉及动作、失效、阻断风险、交易与退出并可能改变判断。
2. **值得继续看**：出现可溯源的项目专属进展，尚未跨越行动门槛，但首要缺口和下一触发已经具体。
3. **保持观察**：没有需要优先阅读的新事实，继续保留在全部机会目录。

“反身性管理”和“失效/排除”只有在出现新的收紧、退出或失效事实时进入“现在必须看”；不能因为标签本身长期占用首页。

### 5.2 首页资格

首页最多展示 5 个项目。项目必须同时满足：

- 已选定唯一展示案例；
- 五段式摘要完整；
- 优先理由不是通用模板；
- 所用证据可回指本项目证据或原始记录；
- 证据未明确过期；
- 变化数值满足单位和比较基准要求；
- 数据状态不是无法确认的一致性错误。

不满足时留在全部机会，并显示“资料不足，暂不进入优先展示”；不得使用通用文案补足 5 个名额。

### 5.3 唯一展示案例

一个项目存在多个候选案例时，只选择一个前台展示案例：

1. 最新已发布机器结论；
2. 若时间相同，选择 `candidate_cases.updated_at` 更新较新的案例；
3. 再相同按 `case_id` 升序确定。

后台保留所有案例，前台项目数按唯一项目计算，不把 602 个案例冒充 602 个项目。

### 5.4 无分数排序

层内使用固定字典序，不计算或保存数值分：

1. 已改变动作或当前可行动；
2. `可能收紧` 优先于 `可能改善`，风险保护优先；
3. 影响维度顺序：失效/阻断风险 → 当前动作 → 交易与退出 → 价值捕获/剩余凸性/点火距离 → 证据成熟度；
4. `confirmed_fact` 优先于 `high_confidence_inference`；项目方陈述和未验证线索不能单独进入首页；
5. 变化时间倒序；
6. 项目规范名称升序作为稳定兜底。

前台必须能用普通语言复述排序理由，并回指实际字段；不得显示或暗存“综合分”。

## 6. C2.0-02 变化事件链与影响解释

### 6.1 去重

同一项目、同一运行、同一语义字段、相同起止值的记录只显示一次；所有证据引用合并并去重，原始记录不删除。

同一项目同一轮的多字段变化合并为一张项目事件卡，按影响维度列出子变化，不按字段平铺多张卡。

### 6.2 连续事件链

同一项目、同一语义字段、相邻时间不超过 24 小时的连续变化形成一条事件链。默认显示最初状态、最终状态和净变化；展开后按时间查看全部步骤。

- 最终状态等于最初状态：标记“尚不改变判断”，默认不进入首页。
- 中途出现动作变化、失效或阻断风险：该步骤必须保留并在展开层明确显示，不能被净变化抹掉。
- 不同项目、不同语义字段或时间间隔超过 24 小时不得合并。

### 6.3 影响标签

每条前台变化只使用：

- `可能改善`
- `可能收紧`
- `尚不改变判断`

标签只解释相对方向，不直接产生动作。实际动作已经变化时，在正文写清“当前动作已由 A 变为 B”，影响标签仍按改善或收紧表达。

### 6.4 数值口径

前台允许直接显示的数值字段及单位：

- `priceUsd`：美元/资产；
- `marketCapUsd`、`fdvUsd`、`liquidityUsd`、`volume24hUsd`、`exitNotionalUsd`：美元；
- `priceChange*Pct`、`estimatedExitSlippagePct`、`modeledExitSlippagePct`：百分比；
- 计数：整数和明确对象；
- 时间：Asia/Shanghai 的日期时间或清楚的相对时间。

所有数值必须同时显示单位、时间范围和比较基准，禁止科学计数法。字段不在允许表、单位缺失或基准不清时，不渲染精确数字，改为“口径尚未确认”，并登记后台质量问题。

## 7. C2.0-03 项目专属五段式摘要

项目详情首屏和首页优先卡片共享同一份摘要事实，但展示密度不同。五段固定为：

1. 当前动作：直接读取现有动作，不重新推导。
2. 当前最强支持事实：选择可溯源的支持证据，必须说明具体事实及其与凸性来源的关系。
3. 当前最大阻断或最大风险：必须包含类别、缺失或风险事实、对行动的影响；不能只写“尚未确认”。
4. 下一触发条件：必须说明下一项可观察事实、由系统还是人工继续处理、下次复查时间。
5. 失效条件与证据时间：显示具体失效条件、所用证据时间和是否过期。

完整性规则：任一段没有可用数据、只有通用模板、无法回指证据，或已明确过期，则 `summaryComplete=false`。前台显示资料不足，不自行补写项目事实；后台列出缺失段和处理入口。

通用模板判定：支持事实、首要阻断或下一触发在规范化后被 3 个及以上项目完全重复，或只有“事实仍在积累”“风险与交易条件仍需继续确认”“代币价值捕获路径尚未核验”“最大风险：尚未确认”等无上下文状态句，均不得用于首页或详情首屏摘要。

## 8. C2.0-04 后台判断质量中心

### 8.1 页面位置

新增后台页面 `app/decision-quality.html`，归入现有一级栏目“模型与规则”，作为该组首个二级入口；工作台概览可在存在 P0/P1 质量问题时提供快捷入口。不得新增第八个后台一级栏目，也不得进入前台发布清单。

### 8.2 七类覆盖漏斗

每个唯一项目在每个维度只能计入一个状态：`已闭环`、`待系统处理`、`待人工确认`。每一层三类之和必须等于当前项目总数。

七类维度：

1. 主体身份；
2. 可购买资产；
3. 价值捕获；
4. 最大可控亏损；
5. 交易与退出；
6. 点火条件；
7. 证据时效。

“已闭环”只表示该问题有明确、可溯源的答案，不等于答案为正面，也不等于可以行动。例如交易与退出明确为阻断，仍属于信息已闭环，但动作继续受阻。

### 8.3 共性阻断排行

按以下固定顺序排序：

1. 对前台行动或失效判断的影响级别；
2. 影响项目数倒序；
3. 过期最久或等待最久；
4. 阻断名称升序。

不按技术任务数量排序。每行必须显示：影响项目数、影响的前台结论数、责任方、系统下一步、最近执行、预计复查时间、失败或部分完成原因以及处理入口。

### 8.4 质量指标

- 项目专属摘要覆盖率；
- 通用模板占比；
- 变化合并率；
- 前台缺少单位数量；
- 过期证据影响项目数；
- 首页有效信号数量；
- 前台摘要可溯源率。

每个指标同时显示分子、分母、定义和生成时间，不只显示百分比。没有分母时显示“无法计算”，不得显示 0%。

### 8.5 闭环队列

判断质量中心本身不新增研究写操作。每一行链接到现有项目、来源、证据或人工复核页面处理；返回后恢复原筛选、页码和滚动位置。已有页面没有可处理入口时，显示“当前没有安全处理入口”，不得临时增加绕过审核的写按钮。

## 9. C2.0-05 排序与空结果诚实表达

- 真实 0 个普通建仓或极限试仓时继续显示 0，不降低门槛。
- 同时说明影响项目最多的三类主要阻断，以及本期是否出现优先阅读的新变化。
- “本期没有需要优先阅读的新机会”是合格结果，不用横向变化或通用模板填充。
- “离行动最近”只能使用现有独立维度和本 PRD 的字典序解释，不修改或复用错配分来伪装优先级。
- 数据不完整时沿用上次有效判断并标明时间和影响范围；不得把数据失败写成市场真实零结果。

## 10. UI 进化包

1. 首页形成三级视觉权重：当前判断最强、优先信号次强、状态与时间弱化。
2. “最值得看”改为最多 5 张有限卡片，首行突出新事实和影响，不重复堆动作标签。
3. “重要变化”按项目聚合为时间线，连续变化默认折叠。
4. 数字统一单位、千分位、方向和时间范围；风险色只用于真实风险、失败和收紧。
5. 项目详情首屏固定五段式摘要，证据链和历史变化渐进展开。
6. 后台判断质量中心使用漏斗、聚合条、可排序表格和有限队列，不使用大量同权卡片。
7. 沿用浅色南极蓝、Logo 和口号，统一正文、辅助文字、标签、警告和间距层级。
8. 1280×720、1440×900、1920×1080 和 Windows 125% 缩放均可用；键盘焦点、加载、真实空结果、部分完成和错误状态分别设计。

## 11. UX 进化包

1. 首页 30 秒完成五问理解任务。
2. 从首页优先信号一次点击进入详情；返回恢复入口、筛选、页码和滚动位置。
3. 重要变化默认只显示“可能改善”或“可能收紧”；用户主动选择后查看“尚不改变判断”。
4. 全部机会保留搜索、筛选和 20 条/页分页，新增可解释排序理由，不提供综合分。
5. 前台任何资料不足都说明系统是否继续处理和下次复查时间；普通用户不承担维护任务。
6. 后台从质量问题进入对应处理页，处理后返回原队列上下文。
7. 系统不能形成可信摘要时显示具体原因和下次复查，不使用无限加载、空白卡片或统一“暂无数据”。
8. 任一优先项目从卡片进入详情后，3 分钟内可展开并核对最强支持事实、首要阻断和失效条件的来源与时间。

## 12. 非目标

- 不修改评分、动作、门槛、L0-L5或生命周期规则。
- 不新增账户、社区、订阅、支付、公开部署或自动交易。
- 不重做 C1.9 的四个前台导航、七个后台一级栏目和前后台壳。

## 13. 版本号与发布门禁

Luna 实现和自测期间，后台左栏继续显示已发布的“当前版本 C1.9”；Luna 不得提前显示 C2.0 已发布。只有 Sol 最终验收全部通过并更新发布状态时，后台唯一版本号才改为“当前版本 C2.0”。前台和项目详情始终不显示业务版本号。
