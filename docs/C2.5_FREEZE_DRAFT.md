# 企鹅投研-凸性｜C2.5 管理者控制面大白话冻结稿

> 文档状态：产品管理者已确认的大白话冻结依据；正式范围由 C2.5 需求锁所列文件共同固定。  
> 当前产品版本：C2.4；D0 是已发布的工程治理基线，不是产品版本。  
> 本稿只定义 C2.5 应该做成什么样；用户已授权冻结，但冻结不授权开发，也不修改现有产品、任务、数据库或调度器。  
> 形成日期：2026-08-14。

## 一句话结论

C2.5 的核心不是“把后台做得更简洁”，而是把工作台真正做成产品管理者的控制面：系统里存在什么任务、正在做什么、依据什么规则、哪里异常、接下来会做什么，以及管理者可以安全地做哪些操作，都必须在工作台里看得见、看得懂、找得到、能追溯。

**界面可以降低理解成本，但不能以优化界面为理由减少管理者可见的信息、可进入的页面或应有的控制权限。**

---

## 一、为什么必须做 C2.5

当前产品已经具备自动运行能力，但管理者的实际控制权没有完整体现在工作台中：

- Windows 中存在唯一调度任务 `PenguinConvexity-C1.8-Scheduler`，它目前实际承载的是 C2.2 时代延续至 C2.4 的统一自动更新入口；仅看名称无法理解它现在负责什么。
- 当前主自动流水线至少包含“新币筛选”和“凸性跟踪”两个可恢复作业，候选生产和历史续跑也由同一调度入口协调，但工作台没有给出完整、统一的任务账本。
- 项目中仍有旧 C1.8、C2.1 的运行入口、状态记录和按需工具。它们哪些仍可执行、哪些只是兼容资产、哪些已经休眠，工作台没有清楚分类。
- 工作台部分页面只显示概览，旧主干维护入口会被当前页面接管逻辑覆盖；管理者无法稳定看到它，更无法确认它是否正在运行。
- 多个本应承担不同职责的后台页面被显示为同一种简化页面，实际任务、来源、规则和操作边界没有展开。
- 规则页面把冻结基线与当前生效的临时放宽试行混在一起，部分字段甚至显示为空。管理者无法直接回答“现在到底按哪条规则运行”。
- 当前运行状态与旧运行记录分散在不同位置，旧记录可能仍显示“运行中”，容易让管理者误判当前真实状态。

这不是单纯的信息展示问题，而是管理者权限没有产品化。C2.5 必须纠正这一点。

---

## 二、C2.5 的产品目标

C2.5 完成后，产品管理者打开工作台，不需要询问开发人员或 Codex，就能独立回答以下问题：

1. 系统里一共有多少个任务入口，哪些会自动运行，哪些只能手动运行，哪些已经停用或只是历史兼容资产？
2. 现在有没有任务在运行？运行到哪一步？最后心跳和检查点是什么？
3. 每个任务上次什么时候运行、结果怎样、下次什么时候运行？
4. 一个任务读取了哪些来源、链、数据库或快照，写出了什么，影响哪些前台页面？
5. 某个来源、链、项目或步骤失败后，影响范围是什么？能否安全重试？
6. 当前真正生效的是哪套规则？冻结基线、临时放宽、版本和生效时间分别是什么？
7. 一个项目为什么通过、等待、撤下或不公开？是哪条证据和哪条规则造成的？
8. 管理者现在可以执行什么操作？操作会影响什么？如何确认结果？能否恢复或回滚？
9. 最近是谁在什么时间改变了任务、频率或规则？改变前后分别是什么？
10. 哪些异常需要管理者决策，哪些只是系统可自动恢复的问题？

达到以上结果，才算“管理者确实掌握产品控制权”。

---

## 三、四项不可降级的管理者权利

### 3.1 完整知情权

凡是可能读取业务数据、写入业务数据、改变快照、改变前台结果、改变任务状态或影响下一次自动运行的入口，都必须进入统一任务账本。

不能因为任务位于 Windows 计划任务、隐藏脚本、API、维护脚本、旧主干入口或手动工具中，就不在工作台显示。

### 3.2 安全控制权

对现役自动任务，管理者必须能够在工作台中执行与任务能力相匹配的安全操作，包括立即运行、恢复、安全暂停、暂停后续自动周期、恢复自动周期和失败重试。

按钮不是装饰。每个可点击操作都必须连接当前唯一真实运行通道，操作后显示明确结果并留下审计记录。

### 3.3 规则透明权

管理者必须能看到当前生效规则、冻结基线、临时覆盖、来源版本、适用对象、影响数量和具体判定理由。

不允许再出现“只有程序知道规则”“必须咨询模型才能理解”“页面有标题但没有数值”或“英文机器码代替产品解释”的情况。

### 3.4 决策与审计权

管理者必须能看到异常、趋势、影响范围和操作历史，能够依据产品事实作出决策，并能追溯每次改变的发起人、时间、前值、后值、影响对象、对应运行和最终结果。

## 四、C2.5 的产品范围

C2.5 在 C2.4 的现有产品和业务主干之上增加完整的管理者控制面，范围固定为：

1. 建立全量任务注册表和管理者可见的任务账本。
2. 建立管理者总览，统一显示运行、健康、异常、待决策和下次计划。
3. 为不同业务对象和不同运行流水线建立独立任务详情页，不把不同任务挤在同一张通用页面中。
4. 为当前支持的安全动作提供真实控制按钮，并明确不可操作的原因。
5. 建立规则透明中心，分开展示冻结基线、当前有效规则和临时覆盖。
6. 建立项目级判定解释，让管理者能沿证据和规则查看结果来源。
7. 建立逐链、逐来源健康视图，显示覆盖、延迟、失败和影响范围。
8. 建立数据快照与交接视图，说明各任务如何产生、消费和发布快照。
9. 建立统一运行记录和管理审计，消除当前状态与历史记录混淆。
10. 用图表、时间线、流程图和明确的层级帮助理解，同时保留可核对的精确表格与详情。
11. 建立一套全产品设计系统：企鹅与南极蓝品牌不变，视觉与反馈对齐 Apple 桌面原则，实际操作对齐 Windows 习惯，并用统一组件消除逐页自造控件。

---

## 五、明确不属于 C2.5 的内容

C2.5 不借管理者控制面建设改变现有投资研究体系或扩大业务范围：

- 不修复或重做六链业务采集能力；逐链问题需要另行立项、冻结和开发。
- 不改变 C2.4 第一关、第二关、四条动态比较路径、两个生命周期池和三个公开状态。
- 不改变贝叶斯更新、L0-L5、风险、剩余凸性、交易性、点火距离或当前动作。
- 不改变“普通建仓、极限试仓、只观察、反身性管理、失效/排除”的行动语言。
- 不新增自动交易，不代替管理者作投资决策。
- 不凭空新增数据，不用模板补足真实零结果，不修改历史事实。
- 不新建第二个 Windows 调度器，不建立第二套运行状态或第二条业务通道。
- 不删除 C2.4 继承的 29 个既有路由，不删除旧入口或历史资产。
- 不读取或连接 RWA 项目的脚本、数据、状态、任务或页面。
- 不改变桌面容器、单实例机制、正式快捷方式或普通用户机会中心的产品边界。
- 不在本版本直接清理旧 C1.8、C2.1 入口；是否迁移、停用或删除必须另做清单并由管理者明确批准。

## 六、整体产品设计规范

这套规范不是把 Windows 软件伪装成 macOS，而是明确借用成熟平台已经验证的设计语言，停止每个页面自行发明按钮、加载、进度、弹窗和鼠标行为。

### 6.1 四层设计优先级

企鹅投研-凸性的产品设计按以下四层执行：

1. **产品事实与安全层**：信息完整、状态真实、操作可恢复、权限不被隐藏。任何视觉优化都不能覆盖这一层。
2. **品牌层**：企鹅 Logo、口号“洞见共识之外的价值”、南极蓝整体色调和既有品牌识别保持不变。
3. **视觉与反馈层**：统一对齐 Apple Human Interface Guidelines 中适用于桌面产品的层级、和谐、一致、内容优先、克制、清晰反馈和低打扰原则。
4. **实际操作层**：软件运行在 Windows 上，鼠标、键盘、窗口、焦点、滚动、右键和系统反馈统一遵循 Windows 桌面操作习惯。

发生冲突时，按以下规则裁决：

- 操作行为冲突时，Windows 习惯优先。
- 品牌颜色冲突时，企鹅与南极蓝品牌优先，但不得牺牲可读性和状态辨识。
- 视觉表达冲突时，在不影响 Windows 操作和无障碍的前提下采用 Apple 桌面视觉原则。
- 可访问性、数据真实性和高影响操作安全高于品牌、动效和视觉相似度。

### 6.2 品牌保持不变

- 继续使用现有企鹅 Logo、产品名和口号，不重新设计品牌标志。
- 继续使用现有南极蓝色值体系，不在 C2.5 重新选一套“苹果蓝”。
- 南极蓝主要用于品牌识别、主操作和选中状态，不能同时被滥用于普通文字、装饰和所有状态。
- 成功、警告、失败、暂停、等待等状态使用稳定的语义色，并同时配中文文字和图标，不能只靠颜色区分。
- 工作台继续以浅色界面为本版本默认方案；C2.5 不为了模仿系统外观擅自新增深色模式。
- 品牌元素要克制地融入标题、导航、重点操作和关键数据，不用大面积 Logo 或装饰抢占业务内容空间。

### 6.3 Apple 桌面视觉原则如何落地

C2.5 对齐的是 Apple 桌面产品的设计原则和成熟控件逻辑，不复制 Apple 专属商标、SF Symbols、红黄绿窗口按钮、系统材质或受限设计资源。

所有页面统一遵守：

- **清楚的视觉层级**：页面标题、说明、主要内容、辅助信息和操作区一眼可分，不靠堆边框表达结构。
- **内容优先**：卡片、阴影、圆角和材质只用于建立层级，不能比任务、规则和数据更抢眼。
- **减少层层嵌套**：宽屏桌面优先在同一层提供足够上下文，避免为了“简洁”连续打开多层弹窗。
- **一致的留白和对齐**：全产品只能使用正式设计系统中的间距、圆角、阴影、字号和分隔线档位，页面不得自建一套数值。
- **克制的颜色和动效**：动效只用于状态变化、空间关系和操作反馈，不做持续闪烁、装饰性漂浮或无意义过场。
- **熟悉的控件**：能用标准按钮、开关、选择器、表格、标签页、弹窗和进度控件解决的，不创造新型交互。
- **窗口可适应**：信息层级必须适应既定窗口尺寸和 Windows 缩放，不通过缩小字号硬塞内容。
- **少打断**：普通成功和轻提示使用页内反馈或通知；只有必须立即确认的高影响事项才使用模态弹窗。

字体不直接分发或冒充 Apple 专属字体。Windows 产品使用合法可用、中文清晰、能正确响应系统缩放的系统字体，通过字号、字重、行高和间距实现 Apple 式清晰层级。

### 6.4 Windows 实际操作规范

鼠标和键盘行为固定遵循 Windows 桌面习惯：

- 左键执行主要操作或选择对象；按钮和链接均使用单击，不把双击作为完成核心任务的唯一方式。
- 右键打开与当前对象有关的上下文菜单，但右键菜单只能提供快捷入口，关键功能必须同时有可见入口。
- 鼠标悬停用于显示控件反馈、完整名称和说明，不用悬停偷偷放置唯一的重要信息。
- 滚轮滚动指针所在的内容区域；不得劫持滚轮执行非预期操作。
- 文本可按 Windows 习惯选择和复制；表格中的项目名称、ID、错误和路径不得故意禁止复制。
- 使用标准箭头、文本、拖动、调整尺寸和等待光标，不制作品牌化鼠标指针。
- 可拖动或可调整尺寸的对象必须有明确把手和对应光标，不能仅靠猜测。
- `Tab` 和 `Shift+Tab` 按视觉顺序移动焦点；`Enter` 或 `Space` 激活当前控件；`Esc` 关闭临时菜单、浮层或可取消弹窗。
- 表格、菜单和标签组在适用时支持方向键；焦点样式只在键盘操作时清晰显示，不能被 CSS 去掉。
- 搜索、刷新、复制等快捷键只有在符合 Windows 通用预期且页面真实支持时才启用；所有快捷键功能同时提供可见入口。
- 窗口必须保留 Windows 的最小化、最大化/还原、关闭、拖动、缩放和贴靠行为，不使用 macOS 红黄绿窗口控制模拟品。
- 应用关闭、窗口返回和页面返回必须保持各自含义；不能把关闭窗口按钮改造成含义不明的后台运行按钮。

### 6.5 按钮统一规范

所有页面使用同一套按钮组件和状态，不得各自绘制：

- 按钮分为主操作、次操作、轻量操作、危险操作和纯图标操作五类。
- 同一操作区域原则上只有一个主操作；南极蓝主按钮不能满页泛滥。
- 按钮文案使用“动作＋对象”，例如“暂停后续周期”“重试失败来源”，不用“确定”“处理”“执行”等脱离上下文的含糊词。
- 危险色只用于确实可能造成中断、覆盖、删除或重大状态改变的操作，不能把普通失败重试也全部做成红色。
- 纯图标按钮只用于用户普遍理解的操作，并必须有悬停说明、键盘焦点和无障碍名称；关键管理操作必须显示文字。
- 每个按钮必须具备正常、悬停、按下、键盘焦点、加载、禁用和失败反馈状态。
- 按钮点击后立即防止重复提交；正在提交时保持原按钮宽度，显示进行中的动作，不能让布局跳动。
- 禁用按钮不得隐藏，必须在附近或悬停说明中解释不可用原因。
- 按钮尺寸、圆角、图标尺寸、间距和文字基线在正式整体设计系统中形成有限档位；页面不得自行创建例外尺寸。

### 6.6 加载、等待和进度条规范

加载反馈必须反映真实任务，不用动画掩盖系统没有状态的问题：

- 预计瞬间完成的页面读取不闪现加载器，避免画面抖动。
- 短时间且范围明确的局部读取使用局部加载，不锁住整个页面。
- 首次加载内容结构时可以使用与真实布局一致的骨架屏，但骨架屏不能伪造业务数值或状态。
- 已知总量或明确阶段的任务使用确定型进度条，显示实际完成量、总量、百分比、当前步骤和最后心跳。
- 无法知道总量的任务使用不确定型进度指示，并明确写“总量未知”及当前正在做什么；绝不生成虚假百分比。
- 后台长任务离开当前页面后仍继续运行，管理者重新进入时读取同一个真实运行状态，不从零播放动画。
- 超过单页等待范围的任务必须允许管理者继续浏览其他页面，并在全局任务区持续显示运行状态。
- 暂停和取消是独立操作，只有底层真正支持时才出现；进度条本身不可点击、不可拖动。
- 加载失败必须在发生位置显示原因、影响和合法重试入口，不能只让加载动画永久旋转。
- 完成后显示真实结果摘要；成功、部分成功和失败必须分开，不能统一提示“操作完成”。

正式设计规范必须为“瞬时、短等待、长任务”确定统一的时间阈值和组件，所有页面共用，不得各自决定什么时候出现转圈。

### 6.7 弹窗、提示和错误规范

- 模态弹窗只用于高影响确认、必须立即作答的阻断事项或无法继续的全局错误。
- 普通成功提示使用不打断工作的通知或页内状态，不弹“操作成功，请点击确定”。
- 输入校验错误显示在对应字段附近，同时在页面顶部给出可定位的错误摘要。
- 弹窗第一句话直接说明发生了什么或管理者要决定什么。
- 高影响弹窗必须列出操作对象、当前状态、影响范围、能否恢复和主次按钮，不能只问“是否确认”。
- 关闭按钮、`Esc`、点击弹窗外部是否关闭，必须根据该操作能否安全取消统一定义；不能每个弹窗行为不同。
- 错误文案包含大白话原因、影响、下一步和可追溯编号；底层堆栈放在展开详情中，不直接铺满页面。
- 空状态必须区分“真实为零”“尚未运行”“筛选后无结果”“无权限”“加载失败”和“无适用数据”。

### 6.8 表格、筛选和详情规范

- 管理后台以表格承担精确核对，图表承担快速发现，两者不能互相取代。
- 表头、列宽、对齐、排序、筛选、分页、选中和展开行为使用同一套组件。
- 数字右对齐，中文文本左对齐，状态使用图标＋文字，时间同时说明口径。
- 关键身份字段、状态、异常和主要操作在 1180×760 下无需横向滚动即可看到。
- 次要列可以按管理者偏好显示或隐藏，但系统不得默认隐藏影响判断的关键字段。
- 行点击只能用于选择或进入明确详情，不能同时暗中触发任务或改变状态。
- 筛选、页码、排序、展开项和滚动位置在进入详情再返回后恢复。
- 批量操作必须先显示已选择对象数量和逐项范围，不允许因筛选状态误操作不可见对象。

### 6.9 动效与性能反馈

- 动效只表达点击反馈、展开收起、页面层级和状态转换。
- 同类动效使用统一时长和缓动，不同页面不得自行创造弹跳、旋转或过场。
- 状态改变先保证文字和数据正确，再播放辅助动效；不能等待动画结束才更新真实状态。
- 持续运行状态使用低干扰反馈，不让整页长期闪烁。
- 支持 Windows“减少动画”或等价无障碍偏好；关闭动效后不影响理解和操作。
- 页面变慢时必须显示真实加载边界，不用复杂视觉效果继续增加性能负担。

### 6.10 无障碍与系统缩放

- 任何状态都不能只靠颜色表达。
- 所有可操作控件可通过键盘到达并具有可见焦点。
- 图标、按钮、输入框、图表和状态必须提供可读取的名称或文字替代。
- 文本、图标和关键边界达到正式设计规范规定的对比度要求。
- 在 Windows 100%、125% 和 150% 缩放下验证，不截断关键文字，不重叠按钮，不让弹窗超出窗口。
- 在 1180×760 和 1440×900 两种既定窗口尺寸下验证完整主路径。
- 图表提供表格或文字等价信息，颜色分组同时使用标签、形状或纹理。
- 不把字号缩小到难以阅读来解决布局问题；内容过多时使用层级、折叠和详情页。

### 6.11 全产品一致性和复用边界

这套规范适用于桌面容器、普通用户机会中心、项目详情和管理者工作台，但不改变前后台产品边界：

- 前台和后台可以共享颜色、字体、间距、按钮、加载、进度、弹窗和无障碍组件。
- 前台和后台仍然使用独立导航、页面壳、责任文案和权限控件，不能为了“统一设计”重新混在一起。
- C2.5 必须完成管理者工作台及本版本触及组件的全面对齐，并对全产品做一致性清单验收。
- 不在 C2.5 范围内的前台业务页面不做无关结构重写；以后任何页面修改必须直接遵循本规范。
- 发现既有页面明显违反按钮、加载、进度、状态真实性或 Windows 操作规范时，必须登记差异；是否在 C2.5 修复按影响范围和继承风险写入正式需求锁，不能静默扩大开发范围。

### 6.12 禁止“自造轮子”

- 优先使用 WPF、WebView2、HTML 语义控件和成熟组件已有的标准能力。
- 全产品只能有一套设计令牌和一套基础控件状态，不能每个页面复制一份 CSS 后各自演化。
- 禁止自定义浏览器滚动逻辑、鼠标指针、窗口控制、复选框、单选框和进度条，除非标准能力无法满足已冻结需求，并在设计规范中写明理由和验收。
- 禁止为了像 macOS 而模拟不符合 Windows 的窗口、菜单、快捷键或鼠标行为。
- 禁止直接复制 Apple 专属设计资源；对齐的是原则、层级和反馈质量。
- 任何自定义控件都必须先证明现有标准控件不能满足需求，并同时补齐键盘、鼠标、缩放、无障碍和全部状态测试。

## 七、页面架构

工作台继续使用浅色管理后台，版本号只在左侧栏底部显示一次。一级栏目固定为以下八类。

### 7.1 管理者总览

总览只负责回答“现在怎样、哪里需要我处理”，不代替详情页。

首屏必须同时显示：

- 自动任务、运行中、等待、暂停、失败、旧版兼容入口的数量。
- 当前唯一 Windows 调度器的真实状态、最近触发、下次触发和最近结果。
- 两个现役主作业的状态：新币筛选、凸性跟踪。
- 候选生产与历史续跑的状态和剩余量。
- 最近一次完整成功时间、最新业务快照时间、当前页面读取时间。
- 六链和全部来源的健康概览。
- 当前生效规则版本和正在生效的临时覆盖数量。
- 最近异常、受影响对象数量和需要管理者决定的事项。
- 最近管理操作和下一批计划运行。

每张卡片都必须能进入对应详情；不在总览堆叠日志全文和全部规则。

### 7.2 全部任务

这是管理者的完整任务账本。任何可执行入口未进入此页，都视为 C2.5 验收失败。

任务按实际状态分类：

- 自动启用：会按照计划自动执行。
- 正在运行：当前存在有效进程、心跳或运行锁。
- 等待运行：已登记但尚未到期，或正在等待上游条件。
- 安全暂停：保留检查点，当前周期不再继续。
- 暂停后续周期：当前运行按安全边界结束，但不再自动发起下一周期。
- 失败：本次运行未完成，需要自动恢复、重试或管理者判断。
- 手动/按需：只在管理者明确触发时执行。
- 旧版兼容/休眠：仍有代码或入口，但不属于当前自动主干。
- 已停用：不可执行，并显示停用原因与批准记录。
- 已完成的一次性任务：保留结果和审计，但不再运行。

工作台不得把“没有出现在当前调度计划中”自动解释为“已经停用”。

### 7.3 任务详情

不同运行流水线必须有独立页面或独立详情路由，至少包括：

1. 新币筛选任务。
2. 凸性跟踪任务。
3. 候选生产与历史续跑任务。
4. 临时产物保留与维护任务。
5. 旧主干与旧版兼容入口。
6. 手动或按需工具。

每个任务详情必须显示：

- 中文名称、机器任务 ID、旧名称或别名。
- 任务目的，以及它不能做什么。
- 当前分类和当前状态。
- 自动/手动触发方式。
- 频率、上次计划时间、实际开始时间、结束时间和下次运行时间。
- 当前步骤、完成量、总量、百分比、最后心跳和可恢复检查点；没有总量时明确显示“总量未知”。
- 输入来源、链、数据库、文件或快照。
- 输出数据库、文件、快照和受影响页面。
- 上游依赖、下游依赖和阻断条件。
- 最近成功、最近失败、连续失败次数和失败原因。
- 失败影响：影响哪些链、来源、项目、结论或页面，是否会导致数据陈旧。
- 当前允许操作、不可操作项及原因。
- 最近运行记录、详细日志入口和管理审计入口。

### 7.4 逐链与来源

该页按“链”和“来源”两个视角切换，不能只显示全局平均值。

每条链、每个来源至少显示：

- 是否在当前任务范围内。
- 最近尝试、最近成功、数据对应时间和延迟。
- 成功、部分失败、失败、无适用数据、尚未运行等明确状态。
- 当前游标或检查点。
- 发现数、接受数、拒绝数、去重数和异常数；不适用时显示“不适用”。
- 失败原因、受影响对象和下一次自动重试时间。
- 是否支持单来源、单链或单分片重试；不支持时说明原因。

“无适用来源”必须显示为 `no_data/无适用数据`，不得继承来源的全局失败状态；真实零结果也不得包装成“采集成功且有数据”。

### 7.5 规则透明中心

规则透明中心固定分为四层：

1. 冻结基线：正式需求锁和规则配置中已经冻结的规则。
2. 当前有效规则：本次运行真正执行的规则。
3. 临时覆盖：经批准正在生效的试行、放宽或紧急覆盖。
4. 历史版本：过去规则、改变原因、验证结果和结束时间。

每条规则必须显示：

- 大白话名称和说明。
- 精确条件、阈值、单位和状态。
- 冻结值、当前有效值以及两者差异。
- 来源文件、版本、批准记录、生效时间和预计结束时间。
- 适用阶段、链、来源、项目类型或对象范围。
- 本轮通过、等待、失败、撤下和不适用数量。
- 至少一个真实通过样本和一个真实未通过样本；没有样本时明确显示“暂无真实样本”。
- 对前台结果和下游任务的影响。

C2.4 已冻结的公开卖出损失基线与当前生效的放宽试行必须分开展示。任何字段缺失时显示“当前数据未提供”和来源位置，不允许留白。

### 7.6 项目判定解释

管理者可以按 `assetId`、项目名或代币检索，看到一条完整的判定链：

`输入证据 → 数据时间 → 规则检查 → 通过/等待/失败原因 → 当前业务状态 → 下游快照 → 前台是否显示`

每个结论必须能回到原始证据或来源记录。综合分只能解释排序和变化，不能被写成单独的凸性依据。

### 7.7 数据快照与交接

该页显示现役任务之间如何通过稳定 `assetId` 和原子快照交接：

- 快照名称、版本、生成任务、生成时间和数据对应时间。
- 当前是否完整、是否陈旧、对象数量和校验结果。
- 消费该快照的任务和页面。
- 最近一次成功交接、失败交接和恢复情况。
- 生命周期状态与凸性跟踪状态必须分开，不得在展示中合并成一个状态。

### 7.8 运行记录与审计

“运行记录”记录系统做了什么，“管理审计”记录谁改变了什么，两者在同一栏目中分标签查看，但数据含义不能混用。

运行记录至少包含：任务、运行 ID、触发方式、开始结束时间、结果、处理量、检查点、产物和错误。

管理审计至少包含：操作者、时间、操作对象、操作类型、改变前、改变后、影响预览、确认记录、关联运行 ID、最终结果和回滚记录。

旧 C1.8、C2.1 记录必须明确标记“历史记录”或“旧版兼容记录”，不得与当前 C2.2/C2.4 运行状态混在一起。陈旧的“运行中”记录必须标记为“状态已过期，不能代表当前正在运行”。

## 八、任务控制按钮与操作边界

### 8.1 必须提供的按钮

现役任务在能力允许时提供：

- 立即运行。
- 从检查点恢复。
- 安全暂停当前运行。
- 暂停后续自动周期。
- 恢复后续自动周期。
- 修改运行频率。
- 重试失败步骤。
- 按来源、链、分片或对象重试；只有底层真实支持时才显示为可用。
- 查看日志。
- 查看影响范围。

按钮不可用时仍应显示，并解释是“任务未运行”“当前步骤不可中断”“底层不支持局部重试”“缺少检查点”还是其他原因，不能直接隐藏。

### 8.2 高影响操作

立即运行、暂停、恢复、改频率、全量重试和任何规则改变都属于高影响操作，必须经过：

1. 显示操作对象和当前状态。
2. 显示预计影响、互斥任务、读写对象和是否会影响前台快照。
3. 管理者明确确认。
4. 后端返回已接受或拒绝的权威结果。
5. 页面显示新的真实状态，而不是先假装成功。
6. 写入管理审计。

不得设置含义不明的“全部启动”按钮。确需批量操作时，确认页必须逐项列出任务、顺序和影响。

### 8.3 安全暂停不是强制终止

安全暂停必须等待任务抵达可恢复边界，保存原子检查点和已完成结果，再进入暂停状态。若当前步骤不能立即暂停，页面显示“暂停请求已收到，将在某步骤后生效”。

强制结束进程不作为普通管理按钮。只有另行定义恢复责任、数据保护和验收规则后，才能设计紧急终止能力。

### 8.4 只能连接唯一真实通道

工作台操作必须复用当前唯一 Windows 调度器、同一业务流水线、同一运行锁和同一状态来源。不得为了做按钮另建调度器、复制任务状态或形成第二业务通道。

## 九、规则能看，也能管，但不能无保护地直接改生产

管理者拥有规则的知情权、提议权、批准权和回滚权，不等于用一个滑块直接覆盖冻结规则。

规则变更固定经过以下流程：

1. 新建变更草案，说明原因、目标和影响范围。
2. 显示冻结基线与拟议规则的精确差异。
3. 使用固定历史样本和当前只读样本重放。
4. 显示通过、等待、失败、撤下数量变化和代表性样本。
5. 显示可能影响的任务、快照和前台页面。
6. 管理者确认是否批准。
7. 生成带版本、批准人、生效时间和结束条件的覆盖记录。
8. 在下一次合法运行中生效，不绕过任务锁和原子发布。
9. 支持回滚至明确版本，并保留完整审计。

若变更触及已经冻结的产品判断体系、数据契约或行动语言，它仍然属于版本范围变化，必须重新冻结，不能仅凭后台操作直接生效。

## 十、图表和交互怎样服务管理决策

图表的作用是帮助管理者更快发现问题，不是替代精确信息。

### 10.1 总览使用

- 状态卡：当前任务数量和需要处理的异常。
- 时间线：最近运行、当前运行和下一次计划。
- 健康矩阵：链 × 来源的成功、延迟和失败分布。
- 小型趋势图：连续运行时长、处理量、失败量和数据陈旧时间。
- 流程图：筛选、跟踪、快照和前台之间的交接状态。

### 10.2 规则页使用

- 漏斗图：进入规则、通过、等待、失败、撤下的数量变化。
- 前后对比：冻结基线与当前覆盖造成的结果差异。
- 分布图：关键阈值附近的样本分布，帮助判断规则是否过紧或过松。

### 10.3 不可取消的精确视图

每张图都必须提供数据时间、口径说明、筛选条件和可展开的精确表格。颜色不能是唯一的信息表达；状态还要有中文文字和图标。图表聚合不能遮蔽真实零结果、缺失数据或部分失败。

## 十一、状态与时间必须可信

页面必须区分三种时间：

- 运行状态时间：系统最后一次确认进程、心跳或锁的时间。
- 业务数据时间：任务实际处理的数据对应时间。
- 页面读取时间：管理者当前打开或刷新页面的时间。

只有同时存在有效运行锁或进程证据，以及未过期的心跳，才能显示“正在运行”。历史记录中的 `running` 不得直接作为当前状态。

快照陈旧、状态陈旧、来源延迟和页面缓存必须分别说明，不能统一写成“数据可能延迟”。所有状态都要显示依据和最后更新时间。

---

## 十二、旧主干和历史入口的处理原则

C2.5 必须先把旧入口纳入账本，再由管理者决定未来如何处理，不能先隐藏或擅自删除。

对每个旧 C1.8、C2.1 入口必须显示：

- 实际文件、API 或任务名称。
- 当前是否仍可执行。
- 是否被现役调度器调用。
- 读取和写入什么。
- 与现役 C2.2/C2.4 流水线的关系。
- 当前分类：现役依赖、回滚资产、手动工具、休眠兼容或待决策。
- 如果误触发会产生什么影响。

现有 Windows 任务名 `PenguinConvexity-C1.8-Scheduler` 必须保留真实机器名称，同时用中文说明“当前统一自动更新调度器”的实际角色。是否改名不在 C2.5 默认范围内，避免在没有迁移和回滚设计时破坏正式运行。

## 十三、权限表达和责任边界

当前单机产品至少区分以下责任：

- 普通用户：只看机会、变化、判断、风险、催化和数据时间，不看任务或管理按钮。
- 产品管理者：看全部任务、规则、来源、异常和审计，执行经过保护的管理操作。
- 系统：按批准的配置自动运行，保存检查点，报告真实状态，不自行扩大权限。
- 开发与验收：修改代码和验证发布，不通过工作台日常按钮绕过版本冻结。

即使首版只有一位本地管理者，工作台也必须明确显示“这是管理操作”，并保留操作者和操作来源；不能因为是单机软件就省略责任记录。

## 十四、异常与待决策中心

系统自动可恢复的问题和需要管理者判断的问题必须分开。

系统自行处理的例子：按既定退避策略重试、从原子检查点恢复、保留已成功分片。

需要管理者决定的例子：

- 同一任务连续失败并超过既定次数。
- 失败影响前台最新快照或造成明显数据陈旧。
- 某个旧入口仍可写入现役数据但身份未确定。
- 临时规则覆盖即将到期，需结束、续期或正式纳入新版本。
- 运行频率改变会造成来源额度或任务冲突。
- 快照校验失败，不能安全发布。

每个待决策事项必须提供事实、影响范围、可选操作、风险和推荐的安全默认项；系统不能替管理者默默选择高影响方案。

## 十五、C2.5 验收画面

以下场景必须使用真实桌面产品和真实只读状态验证；涉及控制按钮时使用可恢复、不会破坏业务数据的受控测试任务或专用验收配置。

### 场景 1：十秒内掌握全局

管理者打开工作台后，十秒内能看到自动任务数量、运行中任务、失败任务、最近完整成功、下一次运行、当前规则覆盖和待决策事项。

### 场景 2：找到唯一 Windows 调度器

管理者能找到 `PenguinConvexity-C1.8-Scheduler`，看懂它当前真实作用、触发命令、最近结果、下次运行以及它协调的现役作业，不需要咨询 Codex。

### 场景 3：控制现役自动作业

管理者能分别进入新币筛选、凸性跟踪和候选生产/历史续跑详情，在合法状态下执行立即运行、安全暂停、恢复或暂停后续周期；确认页和最终状态均与真实后端一致。

### 场景 4：旧主干不再隐身

所有旧 C1.8、C2.1 任务、API 和手动入口都在账本中有分类，管理者能看到它们是否仍可执行、是否被现役调度器调用以及误触发影响。C2.5 不以隐藏入口代替治理。

### 场景 5：规则不再是黑箱

规则页同时显示 C2.4 冻结基线与当前生效的放宽试行，所有阈值、单位、状态、版本和影响数量完整；不出现空值。选择任一 `assetId`，能看到它为什么通过、等待、失败或不公开。

### 场景 6：运行记录不互相冒充

当前 C2.2/C2.4 运行记录和旧 C1.8/C2.1 记录有明确标签；陈旧的“运行中”不会被展示为当前正在运行。

### 场景 7：逐链逐来源可判断

管理者能按六链和全部登记来源查看健康、延迟、游标、处理量、失败影响和重试边界；部分失败、真实零结果和无适用数据均如实显示。

### 场景 8：任务登记完整性

验收脚本独立枚举 Windows 任务、隐藏运行脚本、服务端可执行 API、手动工具和恢复入口，并与工作台任务账本逐项对账。任何可执行入口未登记，C2.5 核心验收直接失败，不能用其他低优先级通过项抵消。

### 场景 9：继承零删除

C2.4 的 29 个唯一角色路由全部保留并返回正确内容；普通用户前台、项目详情、桌面容器和既有业务能力不因控制面重构而丢失。

### 场景 10：真实桌面可用

在 1180×760 和 1440×900 窗口下验证总览、任务表、详情、规则对比、筛选、返回、滚动、单实例和窗口记忆。重要状态和按钮不被遮挡，不依赖横向滚动才能完成核心操作。

### 场景 11：审计可追溯

每次受控管理操作都能查到操作者、时间、前后状态、影响预览、确认结果、对应运行 ID 和最终结果；失败操作也必须留痕。

### 场景 12：没有第二套控制状态

工作台显示值、API 返回、运行状态文件、进程/锁和调度器状态逐项核对。页面不能通过前端本地状态假装任务已启动、暂停或恢复。

### 场景 13：整体设计系统真实一致

对桌面容器、普通用户机会中心、项目详情和管理者工作台建立逐页视觉清单，检查颜色、字体、间距、按钮、加载、进度、弹窗、表格和状态是否来自同一套设计系统。关键控件的正常、悬停、按下、焦点、加载、禁用和失败状态必须使用真实页面截图验收，不能只靠检查 CSS 名称或自动测试数量代替视觉终验。

### 场景 14：Windows 操作没有被苹果视觉破坏

使用真实鼠标和键盘验证左键、右键、悬停、滚轮、文本选择、`Tab`、`Shift+Tab`、`Enter`、`Space`、`Esc`、窗口拖动、缩放、最大化、还原、关闭和贴靠。视觉可以体现 Apple 式层级和克制，但窗口控制、鼠标反馈和键盘行为必须符合 Windows 预期。

### 场景 15：加载和进度全部可信

分别验证瞬时读取、短时局部加载、已知总量长任务、未知总量长任务、暂停请求、离开页面后继续运行、重新进入、部分成功和失败。不得出现虚假百分比、永久转圈、重复提交、进度归零或完成结果含糊。

## 十六、发布硬门槛

C2.5 只有同时满足以下条件才能发布：

- 全量可执行入口与任务账本对账为零遗漏。
- 现役自动任务均有真实、可验证的状态和安全控制路径。
- 冻结基线、当前有效规则、临时覆盖和历史版本完全分离。
- 规则页无空白阈值、无无法解释的机器码、无过期状态冒充当前状态。
- 所有高影响操作均有影响预览、确认、权威结果和审计。
- 没有新增第二调度器、第二状态源或第二业务通道。
- C2.4 的 29 个既有路由零删除继承。
- C2.4 业务规则、普通用户前台和桌面容器继承验收通过。
- 全产品设计系统、通用控件状态和页面差异清单完整，管理者工作台及 C2.5 触及组件全部完成对齐。
- Apple 桌面视觉原则没有被误做成 macOS 窗口仿制，Windows 鼠标、键盘、窗口和系统缩放操作全部通过真实测试。
- 按钮、加载、进度、弹窗、空状态和错误状态完成真实页面视觉终验，不接受只检查代码或自动测试通过数。
- SQLite 完整性、外键、原子快照和当前业务数量按发布时现场值验证。
- 真实桌面主路径和两种窗口尺寸通过。
- 临时产物状态检查完成，无未说明的到期遗留。
- 独立终验通过后，才允许更新正式验收清单、状态和发布记录。

## 十七、程序能力上限必须如实说明

管理者控制面能提高透明度和控制力，但不能承诺程序做不到的事情：

- 能显示来源失败和数据陈旧，不等于能保证外部 API 永远稳定。
- 能显示发现和筛选过程，不等于能保证发现所有新项目。
- 能解释规则和证据，不等于保证研究结论或投资收益正确。
- 能发起安全重试，不等于任何失败都可以局部恢复。
- 能显示旧入口，不等于自动决定这些入口应保留还是删除。
- 能管理规则版本，不等于可以绕过已经冻结的产品范围。
- 能控制研究任务，不等于自动交易或代替管理者承担投资责任。

## 十九、本稿已经明确的产品决定

以下不是待实现阶段讨论的可选项：

1. 管理者知情权是 C2.5 第一优先级。
2. 所有自动、手动、隐藏、恢复和旧版可执行入口必须登记，不得隐藏。
3. 自动运行任务必须在工作台显示真实运行情况和与能力匹配的手动控制按钮。
4. 规则必须显示冻结基线、当前有效值、临时覆盖、来源版本和项目级理由。
5. 图表用于帮助判断，但精确表格、时间、口径和详情不可被图表替代。
6. 不同业务对象和不同运行流水线必须有独立详情，不使用一张通用页面冒充完整后台。
7. 不可用按钮必须说明原因，不能直接消失。
8. 高影响操作必须预览、确认、返回权威结果并留审计。
9. C2.5 复用唯一调度器和业务通道，不新增第二套控制状态。
10. 旧主干先透明登记，再由管理者另行决定治理方式；本版本不擅自删除。
11. C2.5 不改 C2.4 投资研究规则，不借控制面建设修复六链业务能力。
12. 任务登记完整性、规则无黑箱和状态不矛盾属于核心门槛，不能被其他通过项抵消。
13. 企鹅、口号和南极蓝品牌不变；产品视觉与反馈对齐 Apple 桌面设计原则，鼠标、键盘、窗口和实际操作对齐 Windows 规范。
14. 全产品共用一套设计令牌和基础控件，不再逐页自制按钮、加载、进度、弹窗、状态和鼠标行为。
15. 视觉统一不能合并前后台边界，也不能用“苹果风格”模拟不符合 Windows 的系统操作。
