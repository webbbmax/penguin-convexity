# C2.2 候选生产化修复：大白话冻结讨论稿

状态：用户已确认三项选择，保留为正式化依据  
日期：2026-08-11  
作用：解决“459 万事件候选看起来全部筛过、实际只有 161 个进入硬门槛”的覆盖缺陷  
授权边界：用户只授权正式冻结；本稿不是编码授权，不修改现有 C2.2 需求锁，不启动历史扫描

## 一句话结论

459 万条记录要由一个隐藏、可恢复、可暂停的后台程序逐步生产化；日常新发现优先，历史积压在后台持续补扫。新币筛选先形成一个较宽的“可跟踪资产池”，凸性跟踪对这个宽池持续计算；只有身份和产品证据闭环的 A/B/C 项目进入公开机会前台。D 类和身份待确认资产可以在后台跟踪，但不能冒充已确认项目公开展示。

## 一、为什么必须修复

截至 2026-08-11 的只读核验结果：

| 当前阶段 | 数量 | 真实含义 |
|---|---:|---|
| DEX 事件衍生候选 | 4,590,214 | 不是项目数，包含旧币新池、交易对两侧资产、包装资产和大量仅创建对象 |
| 仍停在 `discovered` | 4,585,726 | 尚未完成基础扫描 |
| T0 已核验 | 4,365 | 其中 4,259 个来自后续增量发现 |
| 真正执行硬门槛 | 161 | 当前硬门槛实际分母 |
| 硬门槛通过 | 11 | 是 161 个中的 11 个，不是 459 万个中的 11 个 |

当前程序存在两个覆盖缺陷：

1. Gate 0 历史候选需要先获得市场和身份线索，但市场采集入口又要求对象已经有身份或产品证据，形成循环依赖。
2. 硬门槛评估只读取已经映射项目或已经是 A/B/C 的对象，大多数候选没有明确的基础扫描去向。

当前测试只证明“前台数量等于已经通过硬门槛的数量”，没有证明“所有应该基础扫描的对象都真正进入过扫描”。修复后必须增加分母覆盖验收。

## 二、四层处理规则

### 第一层：本地基础扫描

这一层覆盖全部候选，不调用外部接口，不随机抽样，不设置热门项目上限。

程序可以直接排除：

- 链和合约地址完全重复；
- 地址、时间或事件关系无效；
- 当前已经到第 91 天；
- 通过明确地址表识别的稳定币、包装币、桥接资产、LP 代币和常见报价资产；
- 已由本项目主库确定为旧资产连续部署、包装或桥接关系的对象；
- 可靠数据已经证明存在更早公开流通时间且早于 90 天窗口的对象。

程序不得仅凭名称、Symbol、简介、社交文字或 Meme 关键词排除项目，也不得因为缺少身份资料直接写成失败。

本层输出必须为每个对象保存一种明确去向：

- `local_pass`：进入市场确认队列；
- `known_continuation`：已知旧资产连续关系；
- `known_quote_or_wrapped_asset`：已知报价、稳定或包装资产；
- `outside_90_days`：已到第 91 天；
- `invalid_event_or_identity_conflict`：可复现的事件或身份冲突；
- `local_pending`：现有本地事实不足，等待后续确定性数据。

### 第二层：公开市场确认

只对第一层留下的对象调用批量市场接口，按链和地址确认：

- 链和合约地址匹配；
- 存在来源已经索引的公开交易池；
- 对象在交易池中的资产方向明确；
- 当前真实窗口至少观察到 1 笔买入和 1 笔卖出。

这一层不设置固定流动性、成交额、市值、FDV、TVL 或综合分门槛。

状态固定为：

- `market_confirmed`：市场、方向、买入和卖出均已确认；
- `waiting_for_trades`：市场存在，但买入或卖出尚未形成；
- `market_not_indexed`：当前来源没有索引到市场；
- `market_identity_conflict`：链、地址、交易池或资产方向冲突；
- `source_pending`：额度、连接、配置或程序问题，本轮不能完成。

`waiting_for_trades` 和 `market_not_indexed` 不永久淘汰。在第 90 天以前出现新证据，可以自动重新进入。

### 第三层：进入后台凸性跟踪

满足以下条件即可进入后台凸性跟踪池：

1. T0 在接入范围内可复现；
2. 当前处于第 0—90 天；
3. 公开交易池、链、地址和资产方向一致；
4. 已观察到至少 1 笔买入和 1 笔卖出；
5. 没有已经确认的卖出失败、冻结、黑名单或其他硬交易阻断。

以下缺失不阻止进入后台跟踪，只形成待补全状态：

- 项目身份未确认；
- GitHub 或其他产品证据未取得；
- 安全来源暂时无返回；
- 供应、持仓、产品使用或历史窗口暂不完整。

进入后台跟踪后，程序继续计算市场、成交、流动性、供应、地址、异常、贝叶斯证据和可用的强路径。缺失因子保持 `unavailable`，不写成 0，不跨因子重新分配权重，也不能因为贝叶斯分数较高自动成为凸性线索。

按当前已完成 T0 核验的 4,365 个对象做影子测算，约 3,403 个满足这套宽跟踪条件。该数字只用于证明第二阶段可以获得更有意义的输入池，不是完整历史扫描后的数量承诺。

### 第四层：公开机会前台资格

进入后台跟踪不等于公开展示为项目。公开前台继续要求：

- 合约、资产和交易池身份一致；
- 已形成可复现项目映射；
- 至少有一类合格代码、部署、业务、代币功能或产品使用证据；
- 分类为 A、B 或 C；
- 没有已确认硬交易阻断。

D 类和身份待确认资产留在后台，不进入机会首页、全部机会、重要变化和公开项目详情。以后证据形成后，可以由程序自动升级为 C，再进入前台。

公开前台资格、凸性线索、活跃项目和贝叶斯排序继续是不同维度；本次修复不降低凸性强路径门槛。

## 三、后台程序结构

### 1. 一个后台工作程序，不新建第二个调度器

- 继续只使用现有 `PenguinConvexity-C1.8-Scheduler`；
- 调度器只负责快速检查、启动和恢复；
- 真正扫描由隐藏 Python 工作进程完成；
- 同一时间只允许一个候选生产化写入者；
- 关闭 Codex 或产品窗口后，已经启动的后台工作继续；
- 关机、休眠或进程中断后停止，下次 Windows 登录后从已提交断点恢复；
- 正式运行不显示桌面黑框。

### 2. 两个队列同时存在

高优先级队列：日常新发现候选。  
低优先级队列：459 万历史积压。

两个队列按批次交替运行，日常新增不等待历史清空，历史积压也不能长期饿死。历史队列在六条链之间轮流取分片，避免 Solana 大体量占满全部资源。处理顺序只代表时效，不代表项目质量，不形成年龄权重或年龄分。

### 3. 分片完成即可交给凸性跟踪

不等待 459 万全部完成。任一分片完成并产生 `market_confirmed` 对象后，原子发布该批跟踪资格；凸性跟踪下一轮即可读取。未完成分片和半份结果不得进入正式跟踪快照。

### 4. 断点和恢复

每个分片至少保存：

- 队列类型、链、分片 ID 和输入范围；
- 已处理数量和最后稳定游标；
- 各去向数量；
- 当前来源、调用次数、状态和下一重试时间；
- 已形成的跟踪资格批次 ID；
- 输入文件或数据库范围哈希；
- 最近心跳和最近成功提交时间。

断点使用原子替换。进程异常结束后只能从最后成功提交位置继续，不允许从头重跑，也不允许跳过未提交区间。

## 四、接口调用和重试边界

接口顺序按成本从低到高：

1. 本地归并、时间和连续资产检查；
2. DexScreener 等批量市场、池和买卖确认；
3. 项目网站、合约和资产身份；
4. GitHub 和结构化产品证据；
5. GoPlus 及已接入链上风险；
6. 供应历史、池活动、标准卖出报价和凸性强路径输入。

不能把 459 万对象同时送给全部接口。只有上一层产生明确资格后，才消耗下一层接口。

单次请求继续使用有限重试，不无限快速重连。建议保持 4 次有界尝试；仍失败时保存：

- `quota_limited`；
- `source_failure`；
- `configuration_missing`；
- `program_failure`；
- `no_data`；
- `unsupported`。

来源失败不能改变项目基本事实，也不能冒充项目风险。下一次后台周期从对应来源和对象继续。

### 无市场对象的建议复查频率

该频率只用于节省接口和提高时效，不是质量权重：

| 当前日龄 | 建议复查间隔 |
|---|---:|
| 0—2 天 | 每 6 小时 |
| 3—7 天 | 每 24 小时 |
| 8—30 天 | 每 72 小时 |
| 31—90 天 | 每 7 天 |

用户手动更新只处理新到期对象和明确失败范围，不强制清空全部冷却，也不从头运行 459 万对象。

## 五、更新中心怎么显示

“90 天新币筛选”页面保留日常更新控制，同时新增独立的“历史候选基础扫描”区域，不能与凸性跟踪混成一页或一个进度。

### 日常新币筛选

显示：

- 本轮新增候选；
- 本地基础扫描完成数；
- 市场已确认数；
- 等待交易形成数；
- 已送入后台凸性跟踪数；
- 公开前台新增数；
- 来源失败和单项重试。

### 历史候选基础扫描

显示：

- 已处理 / 总数量和百分比；
- 当前链、当前分片和队列；
- 本地排除、等待市场、市场确认和进入跟踪数量；
- 最近断点、最近心跳和本轮运行时间；
- 有足够稳定样本后才显示预计完成时间及可信度；
- 暂停、继续和失败范围重试；
- 明确写明“不重新扫描 Gate 0 区块链历史”。

历史扫描失败不能把日常新币筛选或凸性跟踪页面标红；必须显示故障所属队列、来源和影响范围。

## 六、数据库和快照边界

- 继续复用 Gate 0 已验收结果，不重新发起 90 天区块链历史扫描；
- 候选状态、分片、游标、来源健康和跟踪资格写入 `data/c2.1-pipeline.db`；
- 不用本次修复重写 C1.7/C1.8 历史主干；
- 正式迁移前分别备份数据库并记录哈希、表结构、核心数量、完整性和外键结果；
- 页面只读取原子快照，不读取正在写入的数据库；
- 测试和桌面点击验收使用数据库副本，不污染正式任务状态；
- 已发布完整快照保留到新快照全部对账通过后再原子替换。

## 七、程序上限

程序可以做到：

- 给接入范围内每个候选留下明确、可复算的处理去向；
- 持续补充市场、身份、产品、风险和凸性证据；
- 从中断位置恢复；
- 在日常新增与历史积压之间公平调度；
- 让符合宽条件的资产先进入后台跟踪，再由证据升级为公开项目。

程序不能做到：

- 证明 459 万对象都是项目；
- 证明覆盖全市场或全球真实 T0；
- 完全识别 Meme、骗局、刷量、女巫和关联钱包；
- 保证外部接口永远有数据；
- 证明项目靠谱、值得投资、可以长期卖出或未来会上涨。

## 八、正式验收标准

### 覆盖和对账

- Gate 0 已导入候选、日常增量候选和去重后总数逐层对账；
- 全部候选最终必须有本地扫描状态，不能长期保持没有原因的 `discovered`；
- 页面必须显示“实际完成基础扫描数”和“实际执行硬门槛数”，不得再把 459 万直接连接到 11；
- 进入跟踪数、后台 D/待身份数、A/B/C 公开数和前台数量分别对账；
- 任一已确认公开资格项目静默遗漏时拒绝发布快照。

### 恢复和长任务

- 人为终止进程、关闭产品、重启 Windows 后从最后原子断点继续；
- 重复启动仍只有一个写入者；
- 已完成分片不重新请求；
- 日常新增在历史积压未完成时仍能独立产生结果；
- 暂停、继续、失败重试和来源冷却范围准确；
- 正式运行黑框为 0。

### 规则和数据

- 本次修复不修改贝叶斯因子权重、P60/P70、美元护栏、强路径、报价护栏和凸性线索定义；
- 缺失不写零，来源失败不写项目失败；
- D/待身份对象只能进入后台跟踪，公开前台数量为 0；
- 第 90 天仍可处理，第 91 天退出；
- 数据库 `integrity_check=ok`，外键异常为 0；
- 正式数据库和用户暂停、频率设置不被验收点击污染。

### 桌面体验

- 从桌面快捷方式进入“90 天新币筛选”可以看懂日常更新和历史扫描的区别；
- 进度在 1180×760 和 1440×900 下完整可读、无横向溢出；
- 手动更新、自动频率、暂停、继续和失败范围重试有明确作用范围；
- 关闭重开后仍显示真实任务和断点；
- 历史扫描、日常筛选和凸性跟踪三个概念不会在同一卡片中混用。

## 九、已确认的产品决定

- 独立可恢复后台工作程序；
- 不在 Codex 对话任务中持续执行 459 万扫描；
- 不重跑 Gate 0 区块链历史；
- 日常新增和历史积压使用双队列；
- 日常新增优先，但历史积压不得饿死；
- 分片完成即可逐批进入凸性跟踪；
- D 类和身份待确认资产可以进入后台凸性跟踪；
- D 类和身份待确认资产不能作为项目进入公开前台；
- 第一层不使用固定成交额、市值、流动性、TVL 或综合分门槛；
- 不降低凸性强路径算法门槛来增加数量。

## 十、用户已确认的最终选择

1. 接受无市场对象按“0—2 天 6 小时、3—7 天每天、8—30 天每 3 天、31—90 天每 7 天”的复查频率；该频率只控制接口成本，不参与质量评分。
2. 接受后台页面名称为“历史候选基础扫描”，日常作业名称继续为“90 天新币筛选”。
3. 接受修复作为 C2.2 发布后的生产化缺陷修复处理，不改名为新产品版本；正式冻结时单独生成修复需求锁和验收清单，不改写原 C2.2 冻结文件。

用户已明确回复“确认”。本稿只作为确认记录；正式范围以独立修复需求锁所列文件为准。冻结不等于编码授权，不启动长任务。
