# 企鹅投研-凸性｜关键决策

更新时间：2026-08-14

## D-001 采用复制并校验，不做破坏性移动

- 决策：先完整复制源项目，再逐文件 SHA-256 校验；旧目录保持原样。
- 原因：保留历史、归档、备份和快速回滚能力，避免一次迁移同时改变路径与数据。
- 结果：新项目独立拥有全部资产；旧项目不是运行时依赖。

## D-002 建立独立桌面壳

- 决策：桌面入口使用本项目的 `desktop/`、`scripts/serve_local.py` 和 `scripts/launch-convexity.ps1`。
- 原因：旧综合壳混合多业务，不能满足独立启动、独立单实例和业务隔离。
- 结果：产品名为“企鹅投研-凸性”，端口 8766，首页直达机会中心，桌面导航只有机会中心、详情、工作台。

## D-003 业务数据与桌面状态全部本地化

- 决策：数据库、游标、任务状态、日志、缓存、备份、窗口位置和单实例锁都属于本项目。
- 原因：允许与其他软件同时运行，并在旧项目不可用时继续启动。
- 结果：不建立到旧整合项目或其他业务目录的运行时引用。

## D-004 公共 API 只共享资源说明

- 决策：公共库只同步 API 目录、文档、凭据环境变量名称和总额度说明。
- 原因：资源发现可以共用，但业务启用、健康、游标、原始数据与任务状态会相互污染。
- 结果：`config/shared-api-catalog.json` 是无密钥快照；本项目自行保存所有运行状态。

## D-005 保持 C1.6-06 产品结构

- 决策：迁移不重做业务模型和机会中心信息架构。
- 原因：M1.0 目标是独立迁移，不是新版本产品开发。
- 结果：保留七段顺序与已有研究结论；不增加通用“今日结论”。

## D-006 研究维度不合并

- 决策：L0-L5、风险、剩余凸性、交易性、点火距离、动作和生命周期路线分开保存与展示。
- 原因：任一维度都不能可靠推出其他维度；合并会产生错误投资结论。
- 结果：错配分只排序研究优先级，动作必须经过身份、证据、价值捕获、风险与交易性硬门槛。

## D-007 迁移验收同时使用脚本与真实用户路径

- 决策：同时执行全量 Python、28 路由、SQLite、浏览器真实点击和 Windows 桌面窗口测试。
- 原因：静态文件、单元测试或选择器超时都不能单独代表实际用户可用性。
- 结果：发布必须证明启动、七段、详情、返回、筛选记忆、窗口记忆和单实例均可用。

## D-008 M1.0 阶段冻结 C1.7

- 决策：M1.0 只把“最大漏斗数据主干一期”写入记忆和状态，不改 C1.7 数据结构与任务。
- 原因：避免迁移与新版本开发混在一起，破坏可归因性和回滚边界。
- 结果：在 M1.0 迁移交付当时，C1.7 被列为下一最高优先级并等待用户在新任务确认。

后续状态：用户已在 M1.0 完成后的新任务明确确认继续 C1.7；该冻结条件已经满足，实施与 M1.0 迁移验收仍保持独立可回滚。

## D-009 原始账本与 Event Schema v2 分层

- 决策：`raw_events` 继续作为不可覆盖的原始事实层，标准事件写入独立的 `normalized_events_v2`，不原地改写历史原始记录。
- 原因：标准字段会演进，但原始证据、原始位置和内容指纹必须长期可恢复、可重放。
- 结果：15,601 条原始事件全部标准化并可回指，重复回放幂等；Schema v2 变化不破坏原始账本。

## D-010 真实零结果与采集异常必须分开

- 决策：来源健康 v2 独立表达健康、真实零结果、静默、失败、额度耗尽、规则缺口、过期和未知状态。
- 原因：把无事件等同于采集成功或把来源静默等同于市场无变化，都会产生错误投资判断。
- 结果：来源游标、高水位、积压、断档、诊断和历史状态都保存在本项目；当前开放断档与积压均为 0。

## D-011 Watcher 登记不等于真实事件

- 决策：项目实体关系先编译 Watcher，再分别展示登记数量、可运行数量和真实采集事件数量。
- 原因：身份待核验、接口缺失或规则未适配的目标不能冒充已经接入；噪声事件也不能直接升格为研究证据。
- 结果：Git、Release、Package、EVM、Solana 五条主线均可审计，登记与采集结果在页面上明确分开。

## D-012 数据主干不改变投资结论体系

- 决策：C1.7 只建设采集、标准化、归属、健康与监控主干；不修改 L0-L5、风险、剩余凸性、交易性、点火距离、生命周期路线或五种动作。
- 原因：数据连续性证明“数据有没有可靠进入”，不证明“项目值得买入”。
- 结果：机会中心仅增加一个数据连续性支撑入口，C1.6-06 七段顺序完整保留；C1.8 未经用户确认不得开始。

## D-013 冷启动先可用、再后台重建

- 决策：本地 HTTP 服务先监听并提供上次有效快照；数据库快照、来源适配和 C1.7 数据主干重建放入后台线程，并与更新接口共用写锁。
- 原因：原启动流程在监听端口前同步重建 23 份快照，实测冷启动约 41.55 秒；用户第一次打开不应等待全量数据重算。
- 结果：当前实测约 1.77 秒进入后台重建状态，后台约 18 秒完成；若后台失败，保留旧快照并通过 `/api/health.startupRebuild` 和服务日志显示失败原因。

## D-014 C1.8 重构展示结构但不改投资体系

- 决策：C1.8 解除 C1.6-06“七类信息全部铺在一个单页长滚动中”的展示冻结，改为一屏决策摘要和独立详情；七类业务语义继续保留。
- 原因：当前首页把 589 个跟踪任务、数百条变化、后台状态和投资结论混在一起，参与建设的用户也无法快速理解，更不适合未来大众展示。
- 结果：C1.8 可以修改栏目名称、页面分层、分页和责任语言，但不得修改 L0-L5、评分、六类维度或五种动作。

## D-015 自动跟踪必须无人值守并标明责任

- 决策：C1.8 建立本项目独立 Windows 调度；每日全量更新、每小时检查到期任务，软件窗口关闭时仍能运行。继续/无变化自动处理，升级/停止由人工确认。
- 原因：C1.7 的“自动跟踪”实际依赖用户先点击一键更新；“待核验、待闭环、待发现、尚未自动执行”没有说明负责人和时间。
- 结果：每个状态固定显示原因、负责人、下一步和时间；普通用户不承担数据采集、催化发现或身份核验。

## D-016 Luna 实现、Sol 独立终验（历史规则，已由 D-046 替代）

- 决策：C1.8 由 Luna 实现和开发自测，Sol 只做最后独立验收与放行；阶段由 `docs/C1.8_PHASE.json` 控制，需求由 SHA-256 锁定。
- 原因：用户希望用 Luna 编码、Sol 做最后验证，同时需要防止忘记切换推理时误把开发自测当作最终验收。
- 结果：等待 Sol 阶段若没有明确“阶段：Sol终验”，任务必须停止并显示切换提示；Sol 发现问题交回 Luna，不直接修改产品代码。

## D-017 Luna 普通实现、Sol 修复与发布（历史规则，已由 D-046 替代）

- 决策：自 2026-08-02 起，Luna 负责普通功能编程和开发自测；Sol 负责实现后的问题修复、阻断清理、独立复验和最终发布。
- 原因：用户不希望在 Luna 修复与 Sol 复验之间重复切换；最终发布责任需要与问题闭环责任保持一致。
- 结果：D-016 中“Sol 不直接修复产品代码”的职责限制被本决策取代。Sol 可以在用户已确认的冻结范围内直接修复问题，但不得扩展产品范围、修改评分/动作/L0-L5或自行开始新版本。Luna 仍不得宣布最终发布通过。

## D-018 自动调度必须保持无窗口运行

- 决策：Windows 计划任务不再直接执行 `python.exe`，改由 `wscript.exe` 调用本项目 `scripts/run-c1-8-scheduler-hidden.vbs`，再以隐藏窗口方式等待调度脚本结束并返回原退出码。
- 原因：当前用户登录后补跑每日任务时，直接启动控制台程序会显示标题为 Python 路径的空白黑框；它不是产品页面，却会被普通用户理解为软件启动故障。
- 结果：桌面快捷方式、桌面服务、自动更新仍保持独立进程和原有任务逻辑；隐藏计划任务实测退出码 0、新增可见 Python 窗口 0。该修复不修改评分、动作、L0-L5、数据来源或跨业务边界。

## D-019 机会中心是前台，工作台是后台

- 决策：机会中心定义为面向普通用户、未来可能公开上线的前台展示产品；工作台定义为管理维护后台。两者不复用导航、页面壳、页脚、管理控件和责任语言。
- 原因：当前从机会中心进入重要变化或催化路径后会加载工作台导航；首页还展示负责人、调度和系统任务，普通用户无法区分投资判断与后台维护。
- 结果：C1.9 必须建立独立前台壳与后台壳。前台只解释判断、机会、变化、风险、催化和数据时间；更新、来源、证据、异常、重试、调度、日志与模型工具只在后台。

## D-020 项目详情不再是顶级导航

- 决策：项目详情只从结论、机会卡片、变化、搜索结果或项目列表进入；删除桌面顶级“项目详情”栏目和全量项目下拉切换。
- 原因：详情是一次上下文阅读，不是独立产品中心；把近 600 个项目放入下拉框既难用，也把详情页错误变成项目管理入口。
- 结果：详情返回必须恢复来源页面、筛选、页码和滚动位置。项目切换只允许搜索或同一结果集中的上一个/下一个。

## D-021 C1.9 只做体验重构与运行状态可见性

- 决策：C1.9 的范围是前后台信息架构、栏目、用语、浅色 UI、交互和长任务进度；不新增核心研究数据能力，不改评分、结论、动作、L0-L5或业务边界。
- 原因：当前最主要问题是用户无法理解产品和无法判断长任务状态；继续增加数据能力会扩大混乱并使体验问题更难归因。
- 结果：允许的最小后端变化仅为在本项目运行状态中增加阶段、计数、心跳和失败聚合等遥测字段，不改变采集结果与研究结论。该范围已于 2026-08-03 冻结，等待 Luna 实现。

## D-022 Sol 规划、Luna 单任务实现、Sol 修复发布（历史规则，已由 D-046 替代）

- 决策：Sol 在一个任务内完成版本规划、产品设计、需求冻结、验收方案和交接包；Luna 在一个任务内完成全部常规编码和开发自测，不拆成多次 Luna 任务；随后由 Sol 独立终验、直接修复冻结范围内问题并发布。
- 原因：用户需要 Sol 的规划与最终判断能力，同时避免 Luna 被拆成多轮后无法判断当前是否已经切换模型。
- 结果：Sol 规划结束与 Luna 自测结束都必须停止并显示下一模型、下一阶段和可复制提示语。模型名称无法可靠识别时先提醒用户在 Codex 界面核对。固定流程见 `docs/MODEL_HANDOFF_PROTOCOL.md`。

## D-023 可见版本号只在工作台固定显示一次

- 决策：面向用户可见的业务版本号只在后台工作台浅色左侧栏底部固定显示一次；机会中心、项目详情、桌面宿主、页眉、页脚、Logo 附近和普通栏目不显示版本号。
- 原因：版本是维护信息，不是普通用户的判断内容。历史版本标签散落在页面上会抢占注意力，并让用户误以为多个版本同时存在。
- 结果：C1.9 验收硬门槛为前台与项目详情可见版本号计数 0、任意后台页面计数 1。内部接口、日志、文档和验收清单仍保留机器版本字段。

## D-024 每次对话必须明确下一步

- 决策：每次最终回复必须明确告诉用户下一步需要做什么；如果当前无需用户操作，则明确给出最高优先级建议。模型交接必须同时写明下一模型、阶段和可复制提示语。
- 原因：用户不应依赖理解代码、阶段文件或回忆模型切换流程来判断工作是否结束和接下来怎么做。
- 结果：普通交付、规划评审、Luna 交接、Sol 终验和发布都使用同一收尾门禁；若有机器可读引用要求，行动提示紧邻引用之前。

## D-025 C1.9 以五份正式文件共同冻结

- 决策：用户于 2026-08-03 回复“按当前方案冻结 C1.9”。正式 PRD、页面唯一归属、UI 与交互规格、前后台用语字典和独立验收计划共同构成冻结需求，并以 SHA-256 需求锁校验。
- 原因：本版本不仅修改栏目，还同时涉及页面壳、用语、视觉、交互和长任务状态；只锁一份 PRD 会遗漏可执行细节，也可能把设计选择留给 Luna 临场决定。
- 结果：当前阶段为 `requirements_frozen_waiting_luna`，产品代码尚未开始。Luna 必须在一个任务内核验需求锁、完成全部常规实现和开发自测，随后切回 Sol 终验、修复并发布。

## D-026 模型交接只使用短口令（历史规则，已由 D-046 替代）

- 决策：用户不再跨模型复制长提示。切换到 Luna 后只回复“已切换 Luna，开始整版开发”；切换回 Sol 后只回复“已切换 Sol，开始终验修复发布”。接手模型自行读取项目内阶段文件、需求锁、交接包和报告。
- 原因：项目上下文已经完整保存在当前目录，重复让用户搬运提示既增加负担，也容易漏掉或复制过时内容。当前 Codex 任务元数据不提供所选模型字段，助手也不能诚实地后台确认模型选择器。
- 结果：模型选择仍由用户在 Codex 界面完成；短口令是阶段启动信号。助手不得猜测模型，也不得因为用户没有复制长提示而拒绝读取项目文件。

## D-027 C1.9 由 Sol 修复后终验发布

- 决策：Luna 完成 C1.9 常规实现与开发自测后，Sol 在不扩大冻结范围的前提下直接修复前台语言、详情上下文、后台信息架构、长任务状态、失败聚合、版本位置和冷启动验收阻断，并重新执行全部正式验收。
- 原因：用户已明确 Sol 对问题修复、阻断清理、独立复验和最终发布负责；把缺陷退回 Luna 会增加模型切换混乱。
- 结果：2026-08-03，A01-A08、B01-B08、C01-C06、D01-D09、E01-E03 共 34 项全部通过，C1.9 阶段改为 `sol_final_acceptance_complete_released`。下一版本尚未定义，等待用户授权。

## D-028 跟踪来源失败必须保留为真实运行风险

- 决策：2026-08-03 14:00 自然调度中 104 个到期跟踪项目因所需来源未在本轮执行而失败，继续按失败保存和展示；不得为了发布把它改写为成功、有数据或“事实零结果”。
- 原因：C1.9 的目标是让运行状态和责任边界可读，不是新增或重写核心采集能力。失败已被按来源聚合，并保留上次有效结论和重试入口，产品体验门槛已满足；来源执行链属于独立运行质量问题。
- 结果：该事实不阻断 C1.9 体验发布，但成为下一最高优先级。任何修复都需用户另行授权，并以自然调度中失败数量真实减少为验收，不得修改评分、动作或研究规则。

## D-029 跟踪来源状态必须按项目归因并同步进入数据主干

- 决策：跟踪任务先运行正式项目市场与退出来源，再按单个项目判断来源成功、无适用数据、部分完成或失败；全局来源统计只用于来源健康，不得直接复制为每个项目的结论。任何更新写入原始事件后，都必须在同一任务结束前做本地增量规范化并重建跟踪页面快照。
- 原因：2026-08-03 的 104 项全失败来自依赖未执行；依赖接通后又因 GoPlus 全局 113 个缺口把 102 项全部污染为部分完成。同期 788 条新原始事件未进入 Event Schema v2，页面快照还可能继续显示到期状态。
- 结果：对真实 102 项重新计算为成功 32、无变化 1、真实部分完成 69、失败 0；两项真实生产复验均完整完成。原始、规范化和可溯源事件重新一致，进度阶段只前进且长等待每 10 秒更新心跳。评分、动作、L0-L5及其他投资规则未改。

## D-030 C2.0 优先解决信号质量而不是继续堆数量

- 决策：下一版本规划为 `C2.0 机会信号质量与可解释决策`。最高优先级是把现有项目和变化压缩为少量、具体、可解释的前台决策信号，并在后台建立判断质量漏斗、共性阻断排行和闭环队列。
- 原因：C1.9 已完成前后台分离，但当前真实页面仍是普通建仓 0、极限试仓 0、只观察 600；首页优先项目大量使用相同理由，“重要变化”有 84 页且多数只是横向变化。继续增加项目或来源会放大噪声，不能提高普通用户的决策效率。
