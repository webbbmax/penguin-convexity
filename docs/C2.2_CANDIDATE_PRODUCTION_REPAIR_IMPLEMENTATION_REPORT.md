## 1. 结论

生产化修复已经落到当前 C2.2 主干，但没有启动 459 万历史候选扫描。正式库只安装了候选状态、双队列、分片、断点、资格批次和运行记录的数据结构；新增生产化记录、分片和运行记录仍全部为 0。

现有日常“90 天新币筛选”保留手动/自动控制。其更新完成后只处理本轮新增或已经到期复查的候选，不会从头扫描历史候选。历史积压使用独立低优先级队列，只有未来获得单独授权后才允许启动；程序和 API 在未授权时均硬拒绝。

## 3. 实现边界

### L1 本地基础扫描

对进入分片的每条候选只用链、合约、事件、T0、连续资产和确定地址表形成一个互斥状态。不使用名称、Symbol、Meme 文案、模型或固定市场数值门槛。

### L2 公开市场确认

按链和地址批量确认公开池、资产方向、当前窗口买入和卖出。买入与卖出各不少于 1 即可确认；流动性、成交额、市值、FDV、TVL 和综合分没有固定进入门槛。缺失、无数据、额度、来源、配置、不支持和程序问题分开保存。

### L3 后台跟踪

T0、0—90 天、公开池、资产方向、买卖事实和无已确认硬交易阻断满足后，可进入后台跟踪。D 类和身份待确认对象的 `projectId` 保持为空；身份、产品、安全、供应和历史缺失保持待补全。

### L4 公开前台

市场确认不会直接把项目放到前台。完整资格批次先进入原 C2.1 硬门槛评估；只有原冻结评估通过且 A/B/C、身份和产品合同完整的对象才把 `frontEligible` 更新为真。半份分片和未完成资格批次不可见。

## 4. 双队列和恢复证据

- 日常队列只接收新对象或到期复查对象；固定测试证明完成对象不会下一轮重复入队。
- 历史队列在未授权时返回 `not_authorized`；本地 API 实测为 HTTP 409，测试前后正式库记录/分片/运行计数均为 0。
- 历史长进程未来启动时不限定单一历史队列，而是在每个分片后刷新日常高优先级队列，并在日常/历史之间交替。
- 历史分片按 Ethereum、Solana、Base、Arbitrum、BNB、Robinhood 六链轮转；固定测试完成一轮六链公平选择。
- 中断后 `running` 分片恢复为 `paused` 并从成员状态继续；已完成成员不再请求。固定测试证明恢复后每个对象只调用一次市场来源。
- 分片发生程序错误时只保存该分片、原子游标、`program_failure` 和下一复查时间；可以单独重试。
- 资格批次在分片末尾一次事务提交。处理中即使个别对象已确认，漏斗和评估仍读不到半份资格。
